# scafo - Agent Guide

`scafo` is a self-hosted, multi-project serverless deployment platform for JS apps. Its state is a registry of JSON objects living in an S3-compatible bucket, mutated only through CAS conditional writes (`If-Match` / `If-None-Match`) — there is no database and no consensus protocol. A single binary is both the node daemon and the CLI.

## Core Principle — Ask First

**When in doubt, ask before acting.** It is always more important to understand the vision and the request than to assume. There is no shame or wasted time in asking clarifying questions — this applies to every conversation and every task in this project.

### Q&A Sessions

When a task involves design decisions, ambiguity, or changes to the project vision, run a structured Q&A session before implementing. Format each question with **2–4 concrete options** the user can pick from, mix, or override with a custom answer. This keeps sessions concise and efficient:

- **Number questions** (Q1, Q2, …) so answers can reference them quickly.
- **Each option** should be a short, self-contained description (1–2 sentences) with a label (A, B, C, D).
- **Avoid open-ended questions** — always propose options. If genuinely unsure, provide your best guesses as options.
- **Group related questions** in a single message rather than asking one at a time.
- After answers, **synthesize** the decisions into a summary and confirm before implementing.
- If the answers reveal further ambiguity, do another focused round — don't assume.

## Commands

- **Build:** `pnpm build` (uses obuild/rolldown)
- **Compile the binary:** `pnpm compile [linux-amd64|linux-arm64]` (`scripts/compile.sh`; `deno compile` over `dist/`, artifacts and their `.sha256` land in `build/`). Needs Deno; nothing at runtime does
- **Test:** `pnpm test` (vitest; the integration suite auto-starts an S3 store container via testcontainers — needs docker. `SCAFO_TEST_STORE=seaweedfs|rustfs` picks the store, default seaweedfs; set `S3_ENDPOINT`/`S3_ACCESS_KEY`/`S3_SECRET_KEY`/`S3_BUCKET` to target an external store instead)
- **Single test file:** `pnpm vitest run test/utils.test.ts`
- **End-to-end, two nodes:** `SCAFO_E2E=1 pnpm vitest run test/integration/e2e-multinode.test.ts` (same images, same flag). One bucket, two Caddy+node pairs on the docker bridge: both serve the same environment, a durable object stays single-owner across them, exactly one node holds the coordinator lease, an ephemeral environment is deleted through the node that is _not_ the coordinator, an environment scaled to `replicas: 1` ends up on exactly one node while the other stops serving it, an environment deployed with `--node-selector tier=fast --replicas all` runs ONLY on the node booted with `SCAFO_NODE_LABELS=tier=fast` — the other answers empty for it — and spreads to both the moment `scafo env selector --clear` lifts the constraint, `docker stop` on the node holding it moves it to the survivor well inside the liveness window a crash would have to wait out (the drain path) and the node serves again when it is started back up, an environment retired through `scafo env` stops being served on both nodes and refuses deletion until `--force`, and killing the coordinator's container hands the lease to the survivor — which then either takes the single-replica environment over or keeps serving it untouched, depending on which node placement had given it to. Needs `SCAFO_BIND_HOST` past loopback — see the runtime-listener rule below
- **End-to-end:** `SCAFO_E2E=1 pnpm vitest run test/integration/e2e.test.ts` (skipped without the flag, so `pnpm test` stays fast). Drives the whole single-node loop against real infrastructure — SeaweedFS, a Caddy the daemon converges through its admin API, celld running the builds, and the built CLI — through `scafo operator keygen --register`, two `scafo deploy --flip` runs and a rollback, asserting what each build serves through Caddy at every step. It then plays the CI-shaped path against a stub OIDC issuer container (`test/integration/_stub-issuer.ts`): `scafo trust set`, then a `scafo deploy --token` into a new environment with NO operator key and NO bucket credential on the calling side, and a token from an untrusted subject that must fail with `trust-mismatch`. It then eases a canary in — `scafo deploy --canary 50`, which deploys WITHOUT flipping and weighs the new build against the alias — samples 40 requests through Caddy and asserts BOTH versions answer on the apex, then promotes the canary with a flip and asserts the split is cleared, the promoted build takes all 40, and the leg that lost is retired. Needs docker, the images `chrislusf/seaweedfs:4.42`, `caddy:2` and `node:24-slim`, and a local `scafo-probe` image carrying node 24, celld and esbuild
- **End-to-end, through Traefik:** `SCAFO_E2E=1 pnpm vitest run test/integration/e2e-traefik.test.ts` (same flag, same topology as the single-node suite with `traefik:v3` in Caddy's place, sharing the node's network namespace). Proves the second ingress end to end and, more to the point, the PULL model: the node publishes its routing at `/v1/ingress/traefik` and Traefik's `http` provider polls it every 2s, so each assertion separates what the node published from what Traefik serves and the suite reports the delay between them. Covers the empty configuration a fresh node publishes, a routeless host (Traefik answers `404 page not found`, where Caddy answers an empty `200`), two `scafo deploy --flip` runs, a `scafo env split --set` over both builds — the other half of the split surface, where the leg being brought back is one whose process was STOPPED when the flip superseded it, so it exercises the restart path; the suite asserts the weighted service the node publishes and the 40-request sample Traefik serves separately, then promotes a leg and watches the weighted service become a plain load balancer again — and `scafo env retire` taking the last environment away, which is the case the driver is built around, because Traefik refuses a configuration whose maps are empty and would otherwise keep serving a stopped build. Shares `test/integration/_harness.ts` with the Caddy suite; the topology is the part worth reading
- **End-to-end, the image:** `SCAFO_E2E=1 pnpm vitest run test/integration/e2e-image.test.ts` (same flag). The only suite that runs the node out of the repository's own `Dockerfile` instead of a bind-mounted worktree, and the only one that is about the ARTIFACT rather than the product: it builds the image through testcontainers, stands the validated single-host topology up around it (SeaweedFS, a Caddy sharing the node's network namespace), and runs the shortest loop that could only pass if the packaging is right — the container runs as uid 10001 with celld, esbuild and `ESBUILD_BINARY_PATH` already on board, the entrypoint takes `sail` and its flags, the node registers itself with nothing mounted in, one `scafo deploy --flip` from the host is served through Caddy, and `docker stop -t 35` exits 0 rather than 137. Everything about product behaviour is left to the two suites that already assert it
- **End-to-end, TLS through the node:** `SCAFO_E2E=1 pnpm vitest run test/integration/e2e-tls.test.ts` (same flag). The only suite about `/v1/storage`, and the only one whose containers share a user-defined docker network rather than the bridge — a CA validating a challenge has to RESOLVE the name it is issuing for, and only a user-defined network has a resolver behind it, so the site name is a network alias on the ingress container and docker's embedded DNS is the whole mechanism. Pebble (`ghcr.io/letsencrypt/pebble`, its shipped configuration copied out of the image with the validation ports moved to 80 and 443) is the CA; the ingress is a Caddy built with the `caddy.storage.scafo` module — `SCAFO_E2E_CADDY_IMAGE`, default `ghcr.io/sandros94/scafo-caddy:edge` — given nothing but the node's storage URL and the `storage-token` the node minted at boot, and holding NO bucket credential. It asserts a real TLS-ALPN issuance, verified against the CA's own issuance root with hostname checking left on; the certificate, its key and the ACME account read back through `/v1/storage` and read again straight out of the bucket as the same bytes; the locks taken and given back with none left behind; a SECOND Caddy on the same storage serving the SAME serial while the CA's log says it signed exactly once; and a wrong or absent token answered `401`

## Architecture

### Module structure (each is a separate export path)

- `scafo` — barrel: `ScafoError` and friends, the registry types, plus the `utils`, `registry`, `auth`, `capacity` and `placement` namespaces
- `scafo/registry` — registry operations: keys, CAS document helpers, coordinator lease, named locks, projects, builds, environments, retirement, varsets, nodes, operator keys, trust, domains, reaper
- `scafo/auth` — node/operator EdDSA tokens and workload OIDC verification
- `scafo/capacity` — cgroup v2 parsing and the capacity planning formulas
- `scafo/placement` — the pure reconcile planner, the pure route renderer, the process-id convention, the port allocator, and the rules that decide which nodes serve an environment: the node-selector match that narrows the candidates, then the rendezvous hashing and replica count that choose among them
- `scafo/daemon` — the node daemon: configuration loading, the HTTP API and its listener, the reconcile loop, deploy intake, and the seam it reports what it did through
- `scafo/drivers/store/uns3` — `CasStore` backed by an S3-compatible bucket via [`uns3`](https://github.com/sandros94/uns3)
- `scafo/drivers/store/memory` — in-process `CasStore` with identical CAS semantics, for tests and local development
- `scafo/drivers/host/node` — `HostReader` probing cgroup v2 and host totals on Node-compatible runtimes
- `scafo/drivers/runtime/celld` — `RuntimeDriver` for celld 0.2.x: process spec, deployment-pointer activation, readiness gate
- `scafo/drivers/supervisor/child` — `Supervisor` running supervised processes as children of the daemon
- `scafo/drivers/ingress/caddy` — `IngressDriver` converging an operator-run Caddy through its admin API
- `scafo/drivers/ingress/traefik` — `IngressDriver` rendering the same routing as a Traefik dynamic configuration, which Traefik polls off the node
- `scafo/drivers/deploy/celld` — `DeployRunner` unpacking an artifact and publishing it with the celld CLI
- `scafo/drivers/archive/tar-zst` — the `.tar.zst` artifact format, packed by the client and unpacked by the node
- `scafo/drivers/observe/access-log` — tails the file an operator's ingress writes its JSON access log to, following it across rotation
- `scafo` (bin) — the CLI. FOUR NOUNS, and then the work. `scafo sail` boots this machine as a node OF the fleet (`--node-labels <k=v,k2=v2>` says what this machine IS); `scafo remote` is the ADDRESS BOOK, git's sense of the word — a NAME for somewhere this operator can reach and the key that speaks there, kept in `~/.scafo` — where `remote add <name> --endpoint <url>` mints a key of its own, `remote list` prints them and `remote export` writes one out as a single portable file a bare machine can operate from; `scafo operator` is the PEOPLE (every human is an operator, admin is a role an operator holds), where `operator keygen` mints an operator key FILE for something else to place, `operator show` prints this operator's PUBLIC half — id and public key, never anything that could sign — as the document a co-worker sends an admin (on stdout alone, so a redirect is a file `enroll` can read), `operator enroll <pubkey> --remote <name> --role admin|operator --projects a,b` admits somebody else's public document over the WIRE on the authority of the caller's own admin key — `--projects` scoping the key to those projects and nothing else, REQUIRED for an operator-tier key, `*` for every project (an admin's to grant), and wire path only, since the ceremony names no projects and so admits only admins — and the same command with the BUCKET flags instead of `--remote` does it bucket-side through `registerOperatorKey` — the ceremony that seeds a new installation and recovers one that has locked every operator out; exactly one of the two must be chosen, and both or neither is a typed refusal explaining the difference — and `operator rotate` replaces the key a remote signs with by registering the new one, proving it with a call made under it, repointing the home and only then dropping the old one (`--keep-old` stops after the flip, `--purge-old` deletes the superseded key file, which is otherwise kept), while `operator list`/`operator revoke --id <key-id>` read (id, TIER, the PROJECTS it may reach — `all` for an admin, `none` for an operator-tier key naming none, and what a rotated key replaced; an operator-tier caller is shown its own key LINEAGE only, with a footer saying so) and prune the set a fleet trusts; `scafo fleet` is reserved for the MACHINES, and ships with `fleet nodes` — a [bucket]-plane listing of the node records (id, labels, liveness from heartbeat freshness, address, drain state), table or `--json`, deliberately not asked of a node because the case it is for is a node not answering. Every command that reaches a node takes `--remote <name>`, then `SCAFO_REMOTE`, then a `"remote"` pin in the project's `scafo.config.jsonc`, then the only remote there is, and otherwise asks or refuses. `--role admin|operator` on any registering command says which tier a key is filed at; the first key of an installation is always an admin. Then the work: `scafo deploy` uploads a build (`--replicas <n|all>` states how many nodes serve the environment, `--node-selector <k=v,k2=v2>` which nodes may, `--canary <weight>` eases it in beside the alias instead of flipping to it), `scafo env` retires an environment out of service and deletes it once it is really meant to go (`--force` skips the wait), targets it at a class of node (`scafo env selector --set|--clear`) and divides its traffic between its builds (`scafo env split --set "buildA=90,buildB=10" | --clear`), `scafo varset` seals an environment's variables, `scafo trust` says which CI issuers may deploy a project, `scafo metrics` and `scafo traces` read what the fleet recorded about itself straight out of the bucket (`--all` on the latter includes the reconcile loop's own periodic passes, which are left out by default), `scafo wg` sets this node up on the WireGuard tunnel. **Pre-launch aliases:** `up` and `keygen` are what `sail` and `operator keygen` were called; both still work, both are HIDDEN from help, both print one deprecation line, and both are deleted at launch (`deprecatedAlias` in `_utils.ts`).

### Key design patterns

- **CAS-only mutation:** every registry write goes through `CasStore.put()` with a precondition. A failed precondition surfaces as `ScafoError("cas-conflict")`; callers recover by re-reading and retrying (`utils.withRetry`).
- **`src/core/**` has zero foreign runtime dependencies.** It may not import third-party packages — only web-standard globals (`crypto.subtle`, `TextEncoder`, `fetch`). The one exception is [`unjwt`](https://github.com/sandros94/unjwt) inside `src/core/auth/**`: own runtime-agnostic libraries are building blocks, not dependencies to avoid.
- **Layers decide what may be imported.** `src/core/**` is pure as above. `src/drivers/**` is where a runtime is allowed: `node:*`, `uns3`. `src/daemon/**` and `src/cli/**` are the application layer and may use established runtime-agnostic packages (`h3`, `confbox`, `citty`, `consola` — the last for CLI prompts only, and imported dynamically so nothing pays for it unless something is asked); of the two, only the CLI reaches for `node:*` — `src/daemon/config.ts` in particular takes its file reader as an argument so it stays runnable anywhere. Every new runtime dependency also belongs in `external` in `build.config.ts`.
- **Core never reaches for a runtime.** Anything impure lives behind an interface core defines and a driver implements (`CasStore`, `HostReader`); the caller wires the two together.
- **One rejection for every bad token:** `src/core/auth` answers expired, replayed, unknown-key, forged and malformed tokens with the same `ScafoError("auth-invalid")` — no message, no detail, reason in `cause`. Only a trust-policy denial is distinguishable (`trust-mismatch`), because that is authorization, not authentication.
- **Operators and nodes are the same key to the verifier, and not to `/v1/operators`.** They live in SEPARATE KEYSPACES — `_scafo/operators/<id>.json` (`OperatorRecord`: `v`, `id`, `publicKey`, `role?`, `supersedes?`, `projects?`, and NO addresses) beside `_scafo/nodes/<id>.json` (`NodeRecord`, machines only) — and the verifier reads EITHER: `_key-cache.ts` resolves a `kid` from both prefixes in one PARALLEL round trip, behind the same 60s cache, so every authenticated route accepts a machine or an operator exactly as it did before and a node calling a peer is still the same caller as an operator calling a node. The routes that administer the trusted set are the exception: they authenticate the token and then ask WHO it belongs to (`callerOperator`, one read of `operators/<id>`), refusing a machine's own with `auth-scope`, so a node that has been taken over cannot write its installation a new operator. That self-refusal is also what makes them unable to empty the set — the caller is always one of the keys.
- **THE NAMESPACE SPLIT, AND WHAT IT CLOSED.** An operator record used to BE a `NodeRecord`, discriminated by a sentinel address (`{internal: "operator", apiPort: 0}`) with the tier hanging off a `NodeRecord.operator` field. One keyspace did two jobs and all of the costs were structural: `listOperators` read every MACHINE of the fleet and discarded the non-operators (a hundred-node fleet paid a hundred reads to answer a question about five keys); a node id and an operator id could COLLIDE; the refusal that kept them apart named the colliding node's INTERNAL ADDRESS — an enumeration oracle any operator-tier key could drive one `POST /v1/operators` at a time, with `revokeOperator` offering a second; and `scafo fleet nodes` listed every operator key as a machine that never answers, because nothing filtered them out. Split, a prefix listing IS the filtered view, `nodes/` holds only machines, and the sentinel, `isOperatorRecord`, `OPERATOR_ADDRESS` and `NodeRecord.operator` are all gone. **ONE ID IS ONE IDENTITY survives as an explicit invariant, enforced from BOTH write sides** — `trustOperator` refuses an id `nodes/` holds, `registerNode` refuses one `operators/` holds — over one shared charset (`assertOperatorId` is `assertNodeId`'s regular expression under another name, deliberately, so neither side can accept what the other refuses). **The address oracle is STRUCTURALLY RESOLVED**: the collision class is gone, the operator-facing refusal says only that the id is taken (no address, no other fact), the bucket-plane one is free to explain itself because its caller is root, and `revokeOperator` answers a machine's id as a plain `not-found` indistinguishable from an id nothing holds. The residual disclosure is EXISTENCE ONLY — a caller learns that some id is in use, which it must, or it cannot choose another. **BREAKING LAYOUT, NO MIGRATION CODE**: pre-public fleets are disposable, so nothing carries records across and an installation re-runs the bucket ceremony. One consequence worth stating: `LEGACY_OPERATOR_ROLE` (a role-less record reads as `admin`) now covers only a record written to the bucket BY HAND, since no older layout survives to produce one — it is kept because a read that DEMOTES is still the wrong direction to be wrong in.
- **A trusted key is not a trusted key: two tiers, k8s-RBAC-shaped.** The bucket is the root anchor — whoever holds its credentials holds the fleet — and keys enter the trusted set two ways: the bucket ceremony (`operator keygen --register`, `operator enroll <pubkey>` with the bucket flags, `remote add --register`), which admits ADMINS only — it names no projects, and an operator-tier key that names none reaches nothing — or an ADMIN adding one through a node, which is where every operator-tier key comes from. `OperatorRole` is `admin` or `operator`, and everything else a token authorizes (deploying, retiring, reading) is the same for both: the split exists to stop a LOCKOUT, which is what one compromised key used to be able to cause when every trusted key could revoke every other. An admin administers the whole set; an operator-tier key may grant no higher than itself (`canGrantRole`) and may revoke ONLY the key its own record `supersedes` (`canRevoke`). That lineage is what keeps rotation working below the admin tier: the expand step registers the replacement with `supersedes: <old-id>` — a node accepts only the caller's own id there, and gives such a key the caller's own tier, so a rotation is never a promotion — and the contract step's `DELETE` is authorized by it. Three guards stand underneath, in `revokeOperator`: self-revocation is refused (naming `operator rotate`, since it is the one removal nothing could verify afterwards), the last trusted key is refused, and the LAST ADMIN is refused — a fleet of nothing but operator-tier keys trusts plenty of keys and can never be administered through a node again. **COMPAT: a record carrying no role reads as `admin`** (`LEGACY_OPERATOR_ROLE`), because every key trusted before roles existed is full-power today and a read must never be a silent demotion. Both routes emit `operator.trusted` / `operator.revoked` (actor, subject, role) into the observability catalog; the bucket ceremony has no daemon and honestly emits nothing.
- **And a second axis over the tiers: PROJECT SCOPE, which is the multi-tenancy layer.** An operator-tier key carries `projects?: string[]` (`TrustedOperator`, `OperatorRecord`), and it is **DEFAULT-DENY: an operator-tier key must NAME what it reaches**. `assertGrantableScope` refuses an operator-tier registration carrying no projects, at both grant sites — `POST /v1/operators` and the bucket ceremony via `registerOperatorKey` — so a key that reaches the whole fleet is one somebody wrote down rather than one nobody thought about. **Absent still means every project for an ADMIN**, which is not a tenant, and for a MACHINE, which carries no operator record; for an operator-tier record it means NOTHING (`canReachProject`), so a hand-written scope-less record stays trusted, authenticates, may rotate itself and may be revoked, and reaches no project until an admin repairs it. **`["*"]` (`WILDCARD_PROJECT`) is how "every project" is said out loud** — the ClusterRoleBinding analog: it must be the SOLE entry (mixing it with slugs is refused rather than read as one of the two, and a hand-written mixed list reads as the literal names it holds), it is exempt from `assertSlug` only in that position, and a FRESH one takes an ADMIN caller — a wildcard key may replace itself with one and may not hand one out beside itself, or the grant would be self-propagating. **An ADMIN is never scoped:** `assertOperatorScope` refuses the combination at write time inside `trustOperator`, so both ways a key enters a fleet meet it; a hand-written record claiming both READS as scoped (`readOperator`), because narrowing is the safe direction to be wrong in. Enforcement is on the NODE API, at the point an operator-authed request names a project, and lives in ONE place — `daemon/_scope.ts`, `assertProjectScope` — reached three ways: `scopedTarget()` in `app.ts` for the five routes whose PATH names a project (retire, unretire, selector, park, delete), `verifyCaller()` in `_intake.ts` for the three that already meet a project there (split, `GET /v1/deploys/:id`, `POST /v1/aliases`), and one explicit call in `POST /v1/deploys`, where the project is in the body and the check therefore has to come after the multipart read — still before a byte is published. The refusal is `auth-scope` (403) and **names only the project that was ASKED for, never the key's own list**: enumerating it would leak tenant names, which is the thing the layer exists to prevent. The workload/CI path is untouched — an OIDC token is bound by its project's own trust policy and has no operator record to be scoped by — and so is a NODE's own token, which is not an operator record at all. Granting follows the role rule one axis over: the effective scope of a registration is `request.projects ?? caller.projects`, bounded by `canGrantScope`, which is one SUBSET test read as sets — an admin's reach and a wildcard key's are every project, a scoped key's is its list, and a scope-less operator-tier key's is the empty set — so a scoped key can neither rotate nor enrol its way wider. **A ROTATION CARRIES A SCOPE OVER; ANYTHING ELSE GRANTS ONE**, and only the second meets `assertFreshGrant` (`_operator-routes.ts`): a replacement for the caller's own key (`supersedes === caller.id`) puts no reach into the fleet that was not already there, which is what lets a broken scope-less record still be rotated and what lets a wildcard key replace itself without minting a second one. `canReachProject` is the read side, and `assertOperatorScope` (record invariants, inside `trustOperator`) is separate from `assertGrantableScope` (what may be handed out) for exactly that reason. **The BUCKET PLANE IS EXPLICITLY OUT OF SCOPE:** bucket credentials are root, and scoping binds operator KEYS on the wire — a multi-tenant platform hands tenants operator keys, never bucket credentials. `--projects a,b` (or `*`) on `operator enroll` is wire-path only — `assertScopedEnrollment` refuses both a scope AND an operator TIER with the ceremony flags, since that path names no projects and so admits only admins — `operator list` shows a scope column reading `all` for an admin, the projects for a scoped key and `none` for a scope-less one, and `operator rotate` carries the scope through untouched. **AND NEITHER READ SURFACE ENUMERATES THE FLEET, which closes the tenant-enumeration finding this bullet used to carry.** `GET /v1/operators` answers an operator-tier caller with its OWN LINEAGE only — its record, the key it supersedes, and any key superseding it, which is exactly what rotation's confirm and contract steps read — hiding every other tenant AND every admin, since an admin is the key worth stealing and the caller may neither grant nor revoke one anyway; the two refusals that used to say "`scafo operator list` says which keys those are" now say "ask whoever enrolled your key". `GET /v1/state` is filtered by `scopedState` (`daemon/_scope.ts`, beside `assertProjectScope` because they are halves of one boundary): placements, parked, processes, reconcile's placements/parked/processes/failures/actions and `coordinator.unplaced` are narrowed to what the caller reaches, while the machine facts — node record, lease, coordinator identity, wake totals, which are pure aggregates with no per-project row — stay. **A node-signed PEER and an ADMIN get the full document, byte-identical**, which the deploy-await hop in `_routed.ts` depends on. Both answers carry `scoped?: true` **whenever the caller is a non-admin operator, including a `["*"]` one that had nothing hidden from it** — the flag states that the answer is scope-dependent, because the alternative makes its absence mean both "everything there is" and "everything you may".
- **A PROJECT IS A RECORD, and an admin can stop one.** `ProjectRecord` (`_scafo/projects/<slug>/project.json`) has always held `v`, `slug`, `placement` and `previewDefaults?`, created idempotently by `createProject` on the first deploy that names the slug — there is no create verb. It now also carries three things a platform BUILT OVER scafo needs. **`createdAt?`** is stamped on first creation and **never backfilled**: absent means the record predates the field, and inventing a stamp on the read that noticed would say the project began the day somebody looked, which is worse than no answer for the one thing it is for (telling a downstream platform how long it has been billing). **`labels?`** is a free-form `Record<string, string>` that **CORE NEVER INTERPRETS** — no key is read, no value branched on, no pair refused — so a platform can tag a project with its billing account or its client and read it back through the API it already talks to; written WHOLESALE (an empty map removes the field), like a node's own labels, because the writer is the authority on what the set now is. **`blocked?: true`** is the full stop. **ABSENT IS NOT BLOCKED and `false` is never written** — a project comes into being on its first deploy, so serving must never depend on a field having been written, and a flag with three states is one somebody reads wrong.
- **BLOCK IS A FULL STOP THAT RIDES THE EXISTING NOT-TO-SERVE MACHINERY.** A blocked project is served nowhere, woken nowhere and deployed to by nobody, while every environment, build, alias, domain and PLACEMENT record underneath it is left exactly where it was — which is what makes unblocking one call with nothing to rebuild. There is no parallel mechanism and nothing downstream knows what a block is: **`readProject` (`daemon/_desired.ts`) returns an EMPTY state for one**, so the project's environments leave by the same door a retired or a reassigned one leaves by — `planReconcile`'s leftover sweep stops whatever still runs (**processes really stop; the ingress refusing new traffic would leave the application up and billing**), and the routing, rendered from what the node serves, stops naming its hosts, so the Traefik snapshot drops them. It is NOT reported as parked: parked promises that a request wakes it. Three more refusals, one per surface that can be asked directly: **`resolveWakeTarget`** checks the resolved target's project at the END, so one question covers platform labels, build-hash recalls and custom domains at once and no future way of resolving a host can skip it (a null target is the same 404 a retired environment gets, and it comes BEFORE the wake stamps or kicks); **`servesHost`** refuses on both routes in, so no certificate is minted for a name that answers nothing and would outlive the block; and **`deploys.ts start()`** refuses at intake off the record `createProject` just returned (no extra read), before a byte is bundled. `assertProjectUnblocked` throws **`project-blocked` (409, not 403)**: nothing is wrong with the caller or its key, and the same request works unchanged once the block is lifted. **It NAMES the project**, which is safe because every path that reaches it has already checked scope — a caller outside the project's scope meets the ordinary `auth-scope` boundary first and never learns the project exists, let alone that it is stopped. `_assign.ts` is deliberately UNTOUCHED: placement decisions survive a block, so nothing waits on a coordinator tick to come back.
- **`/v1/projects` is operator-authed and its writes are ADMIN-ONLY** (`_project-routes.ts`, mounted behind the same `requireOperatorToken` guard as `/v1/operators`). `POST /v1/projects/:project/block|unblock` (idempotent both ways, house verb style like retire/unretire) and `POST /v1/projects/:project/labels` (replaces the map) all go through `adminTarget`, which checks **SCOPE FIRST AND TIER SECOND — the order IS the disclosure rule**: a caller outside the project's scope is refused by the boundary that says nothing about projects it cannot reach, and only a caller already inside meets the tier refusal, which names the rule plainly. An operator-tier key may deploy to a project and retire its environments and may NOT block or label it: blocking exists for a platform stopping a tenant, which is exactly the case where the tenant would rather it did not. `GET /v1/projects` is scope-filtered by the same `canReachProject` and carries `scoped?: true` on every non-admin answer, wildcard included — wave B's rule, verbatim — and it narrows each RECORD as well as the list: **a non-admin's records come back with `labels` STRIPPED** (`tenantView`), because the read side has to match the admin-only write side — labels are the fleet's notes ABOUT a tenant (billing account, client's legal name, and on the dunning path quite possibly why they are about to be stopped), so returning them would publish each to the tenant it concerns. The field is removed rather than emptied: an empty map would be a second spelling of "no labels" AND would leak the one remaining bit — whether notes exist at all — so a labelled and an unlabelled project are byte-identical to a tenant. **`blocked` deliberately STAYS visible** to a scoped caller: it is their own project, they are already living the refusals, and the refusals name the block anyway. **Audit: `project.blocked` / `project.unblocked` (`actor`, `project`)** through the observe pipeline beside `operator.trusted`/`revoked`, landing in the existing `actor` and `project` Parquet columns (no schema change). Labels emit nothing — a tag write is a platform's own bookkeeping and would bury the two lines worth reading. **CLI: `scafo project list|show <slug>|block <slug>|unblock <slug>|label <slug> k=v...`**, the fifth noun, WIRE-ONLY with no bucket fallback (unlike `scafo env`): bucket credentials are root, so a bucket-side path would answer yes to everyone and quietly turn an admin-only verb into one anybody holding the bucket can take.
- **Single error type:** `ScafoError` carries a stable `code` plus an HTTP `status`, and renders to an RFC 9457 problem document. Messages may change, codes may not. **The CLI prints a failure it never wrapped in the same one-line shape, never as a Node stack** (`reportFailure`, `src/cli/_utils.ts`): an `EACCES` on a state directory, a refused connection or a full disk are ordinary ways for a command to end, and a stack trace in front of one says scafo crashed rather than that a directory is not writable. The line is what was raised plus what each of its causes says — the message is where the actionable specifics of a runtime failure are (`EACCES: permission denied, open '<path>'` names the syscall and the path), the frames above it are scafo's own call stack and the one thing an operator cannot act on, and the cause chain is what carries the reason at all for a `fetch` that reports only `TypeError: fetch failed`. Every command funnels into it, so there is one boundary rather than one per command.
- **Single multi-input bundle:** all entry points are `input`s of one `type: "bundle"` in `build.config.ts`, so rolldown code-splits shared core into `dist/_chunks/*`. Adding an entry = add its input (and any runtime dep to `external`).
- **Store drivers are interchangeable:** `MemoryCasStore` implements the same conditional-write contract as the S3 driver, so registry logic can be tested without a bucket.
- **Independent reads overlap; the fan-out is bounded fleet-wide, not per loop.** A read loop over a listing costs one round trip per item, and on a hundred-millisecond bucket a fifty-environment pass spent seconds of that in front of every wake and every rollout. So `utils.mapConcurrent(items, limit, fn)` runs them together — `readDesired`'s environments, `listPlacements`' decisions — under `DEFAULT_CONCURRENCY` (8). Three rules make it safe to keep doing this. It **answers in INPUT order and rejects with the LOWEST INDEX's failure**, which is the error a sequential loop would have thrown, so what a caller reads out never depends on which round trip came back first. **NESTED BOUNDS MULTIPLY**, so a whole pass shares ONE `ConcurrencyGate` rather than each level holding its own — `readDesired` makes one and hands it down. And **a slot is taken at the LEAVES only, never around work that asks for one**: the fan-out over projects is deliberately ungated, because a holder waiting on the gate it is holding a slot from is the one way to deadlock this. Only reads go through it — parallelising writes is a CAS question, not a latency one, and the coordinator's assignment pass is still one environment at a time for that reason.
- **Two clocks, and which one a number belongs to is decided by what it IS.** A STAMP IS AN INSTANT and lives on the registry's wall clock (`nowIso`, `nowDate`, the injectable `RegistryContext.now`): `refreshedAt`, `acquiredAt`, heartbeats, wake stamps, retirement — every one of them is written into a record for ANOTHER NODE to compare against its own clock, and only a shared clock makes that comparison mean anything. A BUDGET IS A DURATION and lives on `utils.startBudget`, which measures with `performance.now()`: how long a lock waiter may go on asking, how long a deploy watches for its build to be routed, how long a held wake request may be held. The distinction is not stylistic. A wall clock STEPS — an NTP correction, a resumed virtual machine, an operator setting the date — while the timers these waits sleep on measure elapsed time, so a budget kept on the wall clock is spent by a forward step without any time having passed: the observed failure was a lock waiter giving up ~3s early on a machine whose clock stepped +2.2s, losing a deploy cleanly and then misreporting how long it had waited. Rule of thumb: if it is written into the bucket, it is wall; if it only ever answers "how much longer", it is monotonic — and nothing ever converts between them.
- **Readiness is two questions, not one.** A runtime's own health endpoint reports on the _process_, not on the application it hosts: a process whose worker fails every single request still answers it with 200, and a process that is draining answers it while refusing everything else. `RuntimeDriver.probeReady` therefore gates on both the runtime health endpoint **and** an application-level request to a configured path, and only calls a process ready when both agree. A process is never sent traffic, and never allowed to replace the one it supersedes, until it has passed both.
- **Idle eviction is a node policy, and the variable stays the driver's.** In celld 0.2.x, evicting an idle cell corrupted its replication chain — acknowledged writes rolled back on restore — which is why the variable was locked away in the first place. celld 0.3.0 (the oldest runtime the driver supports) fixed that, and scafo now turns eviction ON by default: `runtime.cellIdleEvictS` (900, `0` for never) is the ONE clock every cell on a node evicts on. What has not changed is ownership of the variable: the driver strips `CELLD_IDLE_EVICT_S` from anything inherited, refuses it in `extraEnv` and in `runtime.celldEnv` (each refusal names the setting that does carry it), and writes it last, from the policy alone — so no process can evict on a clock its operator never chose.
- **A runtime process's environment is derived, with exactly one door left open.** It is built in four layers, each winning over the one before it: the narrow allowlist of the daemon's own environment (`runtimeBaseEnv` — `PATH`, `HOME`, `TMPDIR`, `TZ`, `RUST_LOG`, and nothing else), then `runtime.celldEnv`, then everything the celld driver derives — bucket credentials, listeners, drain, forwarded-header trust, durability, capacity caps, idle eviction — then the environment's own varset as `CELLD_VAR_*`. The second layer is the OPERATOR'S ESCAPE HATCH (`SCAFO_CELLD_ENV`, `--celld-env`, written `NAME=value,NAME2=value2` inline or as an object under `runtime.celldEnv` in the config file), and it exists because the runtime's own switches — `CELLD_OTEL` and its tuning above all — reach a process through nothing else at all. The driver's own values always win over it, so a name in the driver's `RESERVED_ENV` is REFUSED where it is CONFIGURED rather than at the process that would silently overwrite it: the refusal names the variable and the typed setting that does carry it, because a variable that never takes effect is the kind of misconfiguration an operator finds out about months later. Two limits are part of the surface: a value cannot contain a comma in the inline form (the separator wins — the config file's object has no such limit), and the reserved names are IMPORTED from the driver rather than copied, so the two can never drift.
- **Routing follows readiness, never intent.** `renderRoutes` is pure and takes only what a node actually has running: an environment is reachable at `<project>--<env>.<domain>` (plus `<project>.<domain>` for `production`, plus any custom domain claimed for it) solely when a process serving its alias build has passed its readiness gate, and every ready process is separately reachable at `<project>--<build>.<domain>` so a build stays inspectable for as long as it runs. Hosts whose label would exceed the DNS limit are skipped rather than thrown over — one unnameable environment must not take a node's whole routing with it. The reconcile loop renders this after every pass and hands it to `IngressDriver.apply`, whose failures are recorded in the pass status and never abort it: an ingress that cannot be reached must not stop a node reconciling itself.
- **One routing, two ingresses, and they are reached in opposite directions.** `ingress.driver` selects which ingress a node drives — `caddy` or `traefik` (`--ingress-driver`, `SCAFO_INGRESS_DRIVER`); naming a Caddy admin API on its own still means Caddy, because that setting predates there being a choice. Both drivers are handed the SAME `IngressDesired` after every reconcile pass, and `test/ingress-parity.test.ts` holds them to it: each render is reduced to its `host → upstream` pairs and the two must be identical, whatever the formats do. What differs is the direction. **Caddy is PUSHED:** the driver calls its admin API, owns only the routes carrying its `scafo_` `@id` prefix inside a server the operator also writes into, and adds before it removes so a host that moves is never served by neither. **Traefik PULLS:** its `http` provider polls a URL, so `apply` makes no call at all — it renders the configuration and caches it, the node serves that cache unauthenticated at `GET /v1/ingress/traefik` (a 404 there means this node drives no polled ingress; the seam is `PullingIngressDriver.snapshot()`, checked structurally because the daemon may not import a driver — the ONE standing exception being `config.ts` reading the celld driver's reserved-variable NAME lists, so a `runtime.celldEnv` refusal can never drift from what the driver actually writes; names only, nothing that runs), and Traefik picks the change up on its next poll. So Traefik needs no address configured on the node at all — it is the one doing the asking — and a Caddy setting written alongside it is REFUSED rather than ignored, because it means the operator has misread which of the two applies. Three consequences are worth knowing before choosing: a change reaches traffic one poll later rather than at once; there is no coexistence question, since the document the node serves IS everything that provider routes and the operator's own routers come from their other providers; and **an empty routing must be rendered as an empty document `{}`** — Traefik's decoder REFUSES `{"http":{"routers":{},"services":{}}}` ("routers cannot be a standalone element"), treats the poll as failed, and a failed poll leaves the last configuration in place, so the obvious rendering would keep serving an environment the node has stopped. A host nothing routes also answers differently: Traefik gives `404 page not found`, Caddy an empty `200`. **And so does a weighted host, in a way that matters to anyone measuring one.** Both were pinned by reading the response sequence off the containers for an even split: Caddy 2.11.4's `weighted_round_robin` hands a leg its WHOLE weight in consecutive requests before moving on (`AAAA…(50)…BBBB…(50)…`, cycle = the weights' sum = 100), while Traefik 3.7.10's weighted service is smooth (`ABABAB…`). Both are exact over a full cycle and neither is wrong; what differs is that a short window through Caddy can land entirely inside one leg's block and see a single build. So a split is measured over 200 requests — two full cycles, exact whatever point it starts at — and a dashboard or a canary check that samples fewer than 100 through Caddy is reading noise.
- **A deploy is accepted, then carried out.** `POST /v1/deploys` takes multipart `meta` + `artifact`, ensures the project and environment exist — reading the environment before creating one, because a deploy asks only that it _exist_ and must not be refused for disagreeing with settings it never named, such as the `ephemeral` of a preview environment — answers `202` with a `Location`, and does the rest in the background: publish the artifact through `DeployRunner` (unpack, run the builder, read back the runtime's version id), record an immutable build, and — when the upload asked to flip — move the alias and watch the reconcile loop until a process serving that build is ready. Exactly three states are final (`deployed`, `routed`, `failed`), so a client polls until it reaches one. Missing the routing deadline is a warning and never an error: the build exists and the loop keeps trying. Deploy status is soft state held in memory, so a restarted daemon forgets deploys in flight while the registry remembers everything they had already committed. **AND THE NODE THAT WATCHES IS NOT NECESSARILY THE NODE THAT RUNS IT.** Intake is independent of placement — any node accepts an upload — while WHICH nodes serve the environment is the coordinator's decision, taken after the deploy has landed. So a watch over this node's own processes answered `deploy-not-routed` after the full budget whenever the deploy went through any node but the one placement happened to choose (measured: 2s one way, 124s the other, same build on a two-node fleet), which is a fact about the door the deploy used and not about the deploy. `createRoutedWatch` (`src/daemon/_routed.ts`) therefore asks this node's processes first and, when the placement names OTHER nodes, asks THOSE — `GET /v1/state` over the same guarded peer hop the wake path takes, carrying a fresh node token this node signed for itself, and reading the answer's `reconcile.processes`. **It is a hop rather than a registry read because the registry does not hold the fact:** placement records intent and wake stamps record demand, and nothing anywhere says a node has a READY PROCESS for a build except that node. The contract is unchanged — `routed` still means process readiness — and so is the wire API; only where the fact is fetched from is. Every way of not getting an answer (unreachable, refused, mid-restart) reads as "not yet" and never fails a deploy, the placement is re-read on every look because a deploy that CREATED its environment has no decision to follow until the coordinator's next pass, and the give-up warning names the nodes it was watching.
- **A node is its keypair, and it keeps it.** The id a node registers under and the Ed25519 pair that speaks for it live together in `<stateDir>/node.json`, written `0600` in a directory created `0700`, and are generated only on the first boot. The record in the registry is rewritten on every boot because it is derived state, but the identity behind it is not: a node that regenerated its key would leave a stale public key in the registry and have every token it signs rejected for reasons nothing on it explains. A state file that cannot be read as an identity therefore refuses the boot rather than being replaced — deleting it is a deliberate act — and the configuration only ever _pins_ an id, which replaces the identity outright when it changes.
- **An unclassified network is refused, not assumed.** Every address a node exposes carries traffic that commands it. As soon as the node listener, the internal listener, the advertised address or `runtime.bindHost` reaches past loopback, `scafo sail` refuses to boot until `transport.driver` says which network that is: `wireguard` to tunnel it, `none` to state that it is already private and trusted. There is no default, because the safe-looking one silently exposes a node and the other refuses working setups. A loopback-only node crosses nothing and needs neither.
- **Runtime listeners bind loopback until a fleet needs otherwise.** A runtime process listens on `runtime.bindHost` (default `127.0.0.1`), which is everything a single node needs: its own ingress and its own readiness probe are on that host. A fleet spread over several nodes is the case that needs more — one cell has one owner, and a request that lands on a node that does not own it is forwarded to the one that does, dialling the address that node advertises. Nothing answers there while the listeners are on loopback, so cross-node cell traffic simply cannot work; that is what `runtime.bindHost` widens. It is not a tuning knob: the runtime's peer listener authenticates nobody, so widening it exposes an unauthenticated surface and is therefore gated on the same transport decision as every other exposed address. **EVERYTHING THAT DIALS A PROCESS THIS NODE STARTED TAKES ONE DERIVED ANSWER, `runtimeDialHost` in `src/daemon/config.ts`:** loopback while the listeners are on a wildcard (loopback is among what a wildcard answers on), the EXACT configured address otherwise. Three dialers ask — the readiness gate (`probeHost`), the ingress the routes render against (`upstreamHost`), and the wake surface's hop down to the process it has just brought up — and a dialer that answers it for itself is the bug this exists to prevent: on a tunnelled fleet the listeners are on the WireGuard address and `127.0.0.1` answers nothing, so such a dialer does the whole of a wake and then fails the request it did it for. No end-to-end suite can see it, because their nodes bind a wildcard.
- **A coordinator that loses its renewal stops being one, immediately.** The lease in the bucket is the whole election — there is no consensus protocol. `createCoordinator` renews every `ttlMs/3`, and a renewal that does not land drops the node to candidate _before_ any coordinator-only work runs on that tick, whether the lease was taken away or the bucket merely could not be reached. The two are indistinguishable from the node's side and the safe reading of both is the same, because the node that superseded it is already acting. Deletes cannot be conditional, so the lease is the only thing keeping two reapers apart; a reap that fails for any other reason is recorded, the lease is kept, and the next tick plans again from fresh state.
- **Lease-gated work is forwarded, not refused.** Only the coordinator can carry out a deletion, but which node that is at any moment is the installation's business rather than the operator's. Any node accepts `DELETE /v1/environments/:project/:env`: it does the work when it holds the lease, offers itself once when nobody holds one, and otherwise forwards the request to the holder and returns that answer verbatim. The hop carries a FRESH node token this node signed for itself — never the caller's, which is single-use and was already spent verifying it here — and an `x-scafo-proxied: 1` header, so a forward that lands on a node that does not coordinate either is answered `503` instead of being forwarded again.
- **An environment is served with its variables or not at all.** A node opens its environments' varsets with one AES-256 key, read from a file the operator configures. An environment whose varset this node cannot open — no key, the wrong key, an altered envelope — is recorded as a failure of that one environment and keeps whatever process it already had; the pass carries on and every other environment is served. Starting it unconfigured would come up, pass its readiness gate and serve requests against whatever the code falls back to, which is a misconfiguration nothing reports.
- **Key material is the operator's, never scafo's.** A WireGuard identity is an X25519 keypair, and there is no scalar multiplication on the web-crypto surface every runtime shares. So scafo computes none: `scafo wg init` reads `<stateDir>/wg-private.key` if it is there, shells out to `wg genkey` if it is not, and refuses with the exact command to run if there is neither — the public half likewise, from a file beside it or from `wg pubkey`. Both halves are then persisted `0600`, so a node that has been set up boots on a host that never had wireguard-tools. Bringing the interface up is the operator's step too, because it needs a kernel module and NET_ADMIN: scafo renders `wg0.conf` from the registry's own peer list — every node publishes its key, endpoint and address in its record — prints `wg-quick up`, and stops. A peer's `AllowedIPs` is its own address alone (`/32`, `/128`), never the subnet its record names, because a peer allowed the whole subnet claims every other node's route. Assisted, never magical: an amateur curve implementation inside an operator's private network is a worse outcome than an error message.
- **A tunnelled node lives at its tunnel address.** When `transport.driver` is `wireguard`, `runtime.bindHost` and the advertised address both default to the node's own WireGuard address rather than to loopback or to whatever wildcard the listener bound — inside a tunnel those are the only addresses a peer can actually dial. Explicit configuration still wins. The tunnel's own settings are required in that mode and refused for by name; configured on a node running another transport they are reported as ignored rather than quietly kept.
- **An environment runs on the nodes it was given, and everywhere until it is given any.** Each environment declares how many nodes should serve it (`replicas`: a whole number, or `"all"`), the coordinator decides WHICH nodes by rendezvous hashing over the live ones — `sha256("<project>/<env>\n<nodeId>")`, highest scores win — and writes that to `_scafo/placement/<project>/<env>.json` under its own fence, only when the decision changed. Each node then serves an environment only when the record names it. The defaults preserve exactly what scafo did before placement existed: long-lived environments resolve to `"all"`, ephemeral previews to `1`, and a single-node installation cannot tell the difference. The load-bearing rule is the missing record: **an environment with no placement object is served by every node**, because that is the state of a bootstrap, of a fresh installation, and of every node running a build that predates these records — reading it as "not mine" would take an installation off the air the first time it upgraded. Rendezvous hashing is chosen for stability rather than balance: a node joining or dying only moves the environments that node was involved in, so nothing else restarts.
- **A node is what its operator says it is, and an environment may ask for that.** A node carries `labels` (`node.labels`, `SCAFO_NODE_LABELS`, `--node-labels`, written `k=v,k2=v2` over a slug-ish charset), an environment carries a `nodeSelector`, and a node is ELIGIBLE when its labels contain every selector entry with that exact value — AND semantics, exact values, no operators and no globs, because a selector must mean the same thing to whoever writes it and whoever debugs it a year later (richer expressions stay a compatible extension). Labels are BOOT CONFIGURATION, not runtime state: registration replaces a node's record wholesale, so a label taken out of the configuration is gone on the next start, and relabelling a machine is editing its config and restarting it. The selector narrows the CANDIDATES and rendezvous then picks `replicas` of THOSE, in that order — so `"all"` under a selector means every matching node, and the stability property holds within the eligible set exactly as it holds over the fleet. Two rules carry the feature. **Zero eligible candidates writes NOTHING and deletes NOTHING:** an empty node list would stop the environment everywhere, and removing the record would stop it just as dead (a selector-bearing environment has no run-everywhere fallback), while the likely causes — a node not back from maintenance, a typo'd label, a fleet mid-relabelling — are none of them a reason to take an application down. The last placement stands, stale but serving, and the failure is reported instead (`unplaced`, on the coordinator's status and on `/v1/state`, naming the environment and the selector). **The run-everywhere fallback does NOT apply to a selector-bearing environment:** an environment with no placement record is served everywhere, but only when it is unconstrained — a selector is an explicit statement about which nodes may run it, and serving it on an arbitrary node before the coordinator has decided would violate exactly that, on every node including the excluded ones. So it waits for the coordinator, and `/v1/state.placements` reports the selector beside the decision so both are read together.
- **A coordinator that cannot see the fleet decides nothing.** Placement counts a node live while its `heartbeatAt` — refreshed every 30s, stamped at registration, stopped on shutdown — is younger than three intervals, falling back to `capacity.probedAt` for a record written by a node too old to beat. When NO node is live the assignment pass REFUSES (`placement-unavailable`) and writes nothing at all, because an unreachable bucket, a jumped clock and a fleet mid-restart all read as an empty node list, and the decision that follows from an empty list is "nothing is served anywhere" — every node would stop every process it runs over a hiccup. The last decision standing keeps whatever is running, running. The same fence that gates the reap gates this: a decision recorded at a higher fence belongs to the coordinator that superseded this one and is never overwritten, and a lost CAS is skipped rather than retried, because the winner is another coordinator.
- **A node that is leaving says so, rather than being found out.** A node that simply stops is indistinguishable from one that crashed, and a crash is only noticed once the last heartbeat has aged past the liveness window — 90 seconds in which the coordinator still counts the node among those it hands work to, and its single-replica environments are placed on a process that is already gone. So the FIRST step of a graceful shutdown, before the reconciler, the coordinator or any process is stopped, is a CAS update writing `drainingAt` onto the node's own record; `isNodeLive` then answers false regardless of how fresh the heartbeat is, and the next assignment pass moves the work. It is best effort and never throws — a bucket that cannot be reached must not hold a shutdown open, and failing it the fleet falls back to exactly the timing it had before. Registration rewrites the record wholesale, which is what un-drains a restarted node: a node that has started is a node that serves. There is no hitless handover behind this — the receiving node starts its own process while the leaving one stops — so what draining buys is the delay, not the overlap.
- **An environment is retired before it is deleted.** Deleting is the one act nothing in the registry can undo, and a long-lived environment is the name that outlives every build it ever served — its domains, its variables and its history go with it. So it takes two steps: `retiredAt` marks the environment as on its way out, which takes it out of `readDesired` and therefore out of every node's processes and out of the routing (`renderRoutes` is unchanged and needs to be — it renders what a node actually runs), makes the coordinator give it no nodes and drop its placement record, and makes `/v1/ingress/ask` answer 404 for its claimed domains so no certificate is minted for a name that is going away. Only then, once the grace has run (24h by default, caller-overridable), may it be deleted; the reaper proposes it on the same terms, ephemerality notwithstanding. Every refusal names the route forward — which of ephemeral, retired-past-grace or forced applies, and how much of the grace is left — because a refusal that only restates its rule sends an operator looking for documentation. Retiring is REVERSIBLE for the whole grace and idempotent in the way that matters: retiring twice keeps the first timestamp, because restamping would silently restart the wait. `force` is the single escape hatch and skips both requirements, but never the coordinator lease.
- **A parked host is woken by the request that asks for it.** Scale-to-zero is two layers and one derivation. The CELL layer is celld's own: `runtime.cellIdleEvictS` (default 900, `0` never) evicts idle cells from memory, state safe in the bucket, restored on the next request. The PROCESS layer is scafo's: parked-ness is DERIVED — a wake stamp's age against the environment's `park` policy — and stored nowhere, so there is no state machine to desynchronize and the bucket stays the one truth. An EPHEMERAL environment quiet past `afterS` stops being desired; a SUPERSEDED build with a fresh stamp (inside `buildIdleS`) is desired again as a `recalled` leg, reachable at its own hash host on any environment. A deploy counts as a wake. The routing is what makes a parked name answerable: every explicit route beats them, but each platform domain carries a CATCH-ALL to the node's own daemon (ordered or ranked so it can never shadow an explicit route), and a parked environment's hosts and custom domains are routed to the daemon outright. The daemon resolves the Host (environment name before build id, apex to `production`), ADMITS under the node's `maxConcurrentWakes` — a refusal at the cap writes NO stamp, so a crawler walking a platform domain boots nothing — stamps, kicks the reconcile loop, holds the request through the readiness gate up to `wakeDeadlineS`, and streams it to the process; past the deadline, `503` with `Retry-After`. **WHICH process is the ROUTING's answer, never "whatever this node has ready".** The wake surface picks among the very legs `renderRoutes` weights that environment's hosts over — `servingLegs` in `src/core/placement/routes.ts`, one weighted draw through `pickLeg` per held request — so what the daemon answers and what the ingress answers can never disagree. Answering from any ready process instead served the build a flip had SUPERSEDED for as long as it took a later pass to stop it, minutes on a live fleet, and it is not a corner case: every host without an explicit route falls through here, so during router propagation and for every parked or starting environment the daemon's answer IS the user-visible one. A build-hash host is matched to its exact build and to nothing else, because a recalled build is a leg of no environment. When the routing names no leg — parked, mid-crash, nothing ready — the request falls through to the hold above, which is what starts it. On a fleet, the node the request landed on may not be the node the placement assigned: it FORWARDS the held request to an assigned live node under the `x-scafo-proxied` loop guard (a forwarded wake that is still unassigned answers 503 rather than bouncing), stamping nothing itself. What the bucket does not hold is a permanent `404` in the same problem document every refusal wears — one shape whether the name never existed, the environment was retired, or the reaper took the build; deleted from the bucket means gone, by design. One measured cost to know, ACCEPTED DELIBERATELY rather than mitigated: a recalled build is an EXTRA runtime process on the same nodes, and every runtime process keeps its own node lease in the bucket — so a wake doubles that node's lease writers, and on a store whose conditional writes stall (the stalls arrive correlated: one hiccup can hit every in-flight lease write on the node at once) the runtime's self-fencing can take the PRODUCTION process down alongside the recalled one, seconds of one backend lost. The fencing-on-a-landed-write behaviour is the runtime's to fix; placement-aware waking is the mitigation to reach for only if the storms outlive that fix.
- **A weighted split is one environment serving several builds, and the fleet pointer is why it is delicate.** `EnvironmentRecord.split` (`[{build, weight}]`, integer weights of at least 1 summing to 100, at least two legs) divides an environment's traffic without moving its alias — the alias stays the primary pointer and the rollback target, and `flipAlias` CLEARS the split, because a flip is a full cutover (it warns `split-cleared`, naming the legs it stopped serving, so an operator promoting a canary is told what else just happened). Set it with `scafo env split --set "buildA=90,buildB=10" | --clear`, or ease one in with `scafo deploy --canary <weight>`, which deploys WITHOUT flipping and then weighs the new build against whatever the alias points at — refused, naming `--flip`, on an environment that has never been flipped, because there is nothing to hold the other side and easing traffic onto the only thing that serves an environment means nothing. Both go through `POST /v1/environments/:project/:env/split`, authenticated like `POST /v1/aliases` rather than like the selector: a split moves an application's live traffic between that application's own builds, which is what a project's CI is trusted to do for its own project and no other. Three rules carry the feature.
  - **ACTIVATION AND START ARE PAIRED PER BUILD, AND THIS IS THE WHOLE HAZARD.** celld has ONE deployment pointer per fleet and a process reads it ONCE, while it starts. So a plan phased as "every activation, then every start" — which is what the planner used to emit, and which is invisibly correct while an environment has one build — would leave the pointer naming whichever build was activated LAST, and every process started under it would load that one build. The registry, the routing and the process ids would all still say there are two legs, and the split would serve one build twice with nothing anywhere reporting it. `planReconcile` therefore emits one `{type: "rollout", project, env, build, ports}` per build, which the executor performs as a strict activate → start → gate sequence it cannot interleave; a restart of a crashed leg goes through the same action, so the pointer flips transiently and lands wherever the last rollout left it, which is correct because nothing reads it again until the next process starts. Single build or twelve, one code path. **AND AN ACTIVATION WITH NOTHING TO MOVE READS TWO OBJECTS AND STOPS.** Activation is planned again on every pass until a process for that build is running, so a repeated wake of a build the fleet already serves is the common case and it used to pay four round trips concluding the bucket said what it already said. `activateVersion` reads the fleet-wide pointer, then the NAMED one — which is not evidence about it, because the named pointer is what celld resolves the application through and the two are moved named-first, so a writer interrupted between them leaves exactly that disagreement — and returns having written nothing only when BOTH already select the version at its exact `deploy/<script>/<version>` prefix. That is precisely the state in which the full sequence wrote nothing anyway (`pointAtVersion` declines to rewrite identical bytes), and it is sound because it runs INSIDE the pointer lock: no writer can move either object between the read and the decision not to write. Every doubt takes the full sequence — a missing or unreadable named pointer, another version, another directory, a fleet never deployed to. The one thing it gives up is the upload assertion on that path, and only because nothing moves: the pointer it would refuse to write is the one already standing, and raising cannot unwrite it. **AND PAIRING IS ONLY HALF OF IT, BECAUSE THIS NODE IS NOT THE ONLY WRITER.** The pointer is one object in the bucket: a deploy accepted on ANY node moves it the moment its bundle finishes, and another node rolling the same environment out moves it too — so a deploy landing between an activation and the spawned process's read hands that process the wrong version under the right process id, which is a build-hash host serving another build's code, observed live and reproduced in `test/pointer-lock.test.ts`. Both writers therefore take one fleet-wide named lock per environment, at `_scafo/locks/pointer/<project>/<env>.json`: the same mechanism as the TLS locks — `src/core/registry/locks.ts`, taken with `If-None-Match`, restamped every 5s, takeable by anyone once it has gone 10s unrestamped, polled for every 1s — in a keyspace of scafo's OWN, because the names under `_scafo/tls/locks/` come from the colocated ingress through `/v1/storage` and a caller must not be able to reach across into what the fleet serializes on. A ROLLOUT holds it across activate → spawn and for a bounded moment past the spawn (`POINTER_READ_HOLD_MS` by default, and `runtime.pointerHoldMs` / `SCAFO_POINTER_HOLD_MS` / `--pointer-hold-ms` where an operator states their own, because the bound is sized to a real store's stall ceiling rather than to its usual round-trip and stores differ), and that bounded hold is the whole of the guarantee: the read is a single bucket GET in the runtime's early boot and NOTHING OBSERVES IT — supervised processes inherit the daemon's streams, so their output cannot be attributed to them and the supervisor seam carries no other signal. The readiness gate is deliberately OUTSIDE the lock, because it takes tens of seconds and every other writer of that environment in the fleet would be waiting on them. **AND SO IS EVERYTHING ELSE PAST THE SPAWN, because the hold guards the POINTER rather than the gate.** What the lock promises is about pointer WRITERS — none of them may move it before the spawned process has made its one read — and neither recording that process in the node's bookkeeping nor probing it writes a pointer, so both happen the moment the spawn returns and run alongside the rest of the hold. Made to wait for it they cost a wake the whole hold: the wake surface cannot SEE a process that is in neither the node's process table nor its status, and the gate that would make it servable has not started either, which measured 66% of a median live wake. The rollout still AWAITS the hold before it is done, so the pass owes the process its read window either way. A lock lost while it ran aborts that hold, stops and awaits the runtime's whole process group, and only then reports the original `lease-lost`; bookkeeping is deleted only after confirmed teardown, while a failed teardown keeps the exact ports quarantined and retries the stop on a later pass. A DEPLOY holds it across the whole `celld deploy` shell-out, bundling and upload included, since the pointer moves at the end of them; the flip and the wait for the routing are outside it, because they wait on the reconcile loop whose rollout needs this very lock and holding it there would deadlock a deploy against the loop that carries it out. What it costs: a rollout and a deploy of ONE environment now wait for each other — a rollout waits 5s, then records the failure and lets the pass carry on with every other environment, and a deploy waits 60s, then fails — while two environments never wait for each other at all. Acquisition that runs out is a `cas-conflict` and never a hang, and a lock lost mid-hold (a restamp that did not land, whether refused or unreachable) aborts the section with `lease-lost` rather than carrying on unserialized.
  - **Never reduce serving capacity while any desired leg is unproven.** The old rule — no stop until the replacement has passed its readiness gate — generalizes: a process is stopped only once EVERY build its environment is wanted at has a ready process. A leg whose build record cannot be read (a corrupted or raced registry; the reaper refuses to delete a build any split references) counts as unproven rather than being dropped, so the environment keeps everything it is running and the gap is reported — dropping it would retire the process still serving that leg and hand its share to the others, over a build nobody withdrew.
  - **A split is a routing preference; an outage is not one of the options.** `renderRoutes` weights an environment's own hosts — its label, its apex, its custom domains — over the READY legs only, and redistributes a leg's share proportionally to the ones that are ready (largest remainder, so the shares still sum to 100 and no leg rounds to nothing). A 90/10 whose 10 has not come up yet serves 100 from the 90, and the 10 takes its share back the pass after it passes its gate. Build-hash hosts stay single-backend, so either leg is addressable on its own.
  - **THE DURABLE-OBJECT CAVEAT, and it is the one thing to decide BEFORE splitting anything.** A split divides REQUESTS, not state. Both legs read and write the same bucket, the same varset and the same cells: one durable object has exactly one owner at a time, and which leg owns it is decided by whichever process happened to instantiate it first — not by the weights, not by the request that arrives. So the SAME OBJECT MAY RUN EITHER VERSION during a split, and may hand off between them when a leg restarts. Two consequences. Split stateless and render paths with confidence: they read state they do not own and either version answers correctly. Split DO-heavy logic KNOWINGLY: a change to an object's stored shape, its alarm handling or its internal invariants will be executed by both versions against the same data, so it must be forward- and backward-compatible for the whole life of the split, or the canary corrupts the objects it touches for the 90% that never asked for it. When it cannot be made compatible, the safe shape is a flip (with a rollback) rather than a split, because a flip has one version running at a time.
- **The node holds the bucket credential, so what runs beside it stores THROUGH the node.** An ingress terminating TLS has to keep its certificates, its account key and its issuance locks somewhere durable, and giving it a bucket credential of its own would put the whole registry behind a process whose job is to face the internet. So it stores through `/v1/storage` instead — `PUT`/`GET`/`DELETE` one object, `list` a prefix (recursively, or its immediate children with deeper keys folded into the child they sit under), `stat` a key, `POST`/`DELETE` a named lock. Objects live at `_scafo/tls/objects/<key>`, locks at `_scafo/tls/locks/<name>`, and every value is wrapped in a JSON envelope carrying it base64 beside its `modified` time, because the store's bodies are strings and a certificate's key is DER. **THE SURFACE CARRIES PRIVATE KEYS AND MUST NEVER BE REACHABLE FROM A PUBLIC OR INGRESS-EXPOSED ADDRESS.** It is guarded by one shared token — 32 random bytes, base64url, written `0600` to `<stateDir>/storage-token` on the first boot that finds none and compared in constant time — it is for local or tunnelled callers only, and a node holding no token serves no route here at all rather than refusing each in turn. **AN OPERATOR MAY CHOOSE THE TOKEN INSTEAD, AND IT IS A LIST WHEN THEY DO.** `storage.token` / `SCAFO_STORAGE_TOKEN` / `--storage-token` (comma-separated inline; a string or an array of them in the config file, where an array entry is taken whole) REPLACES minting entirely: nothing random is generated, EVERY listed value is admitted — each compared in constant time, and none of them short-circuiting the comparison of the others — and the FIRST is written to that same file at that same mode, so every file-reading consumer keeps working unchanged. Naming none is byte-for-byte the behaviour above. **THE BOOT LINE SAYS WHICHEVER HANDOFF THIS ACTUALLY IS** (`storageTokenNotice`, `src/cli/_storage-token.ts`), because telling an operator the wrong one sends them to configure something they already hold: a MINTED token exists nowhere but the file, so the file is the distribution channel and mounting it read-only into the process that terminates TLS is the instruction; a SUPPLIED one arrived through the operator's own environment, secret manager or systemd credential, and that IS the channel, so the line names `storage.token` and says only that the file holds the primary too, for whatever reads a path. The minted line is byte-identical to what it has always been — the TLS end-to-end suite reads it out of a node's log. The list is what makes ROTATION EXPAND-CONTRACT and entirely operator-driven: set `[new, old]` and restart the daemon, which admits both; move the callers over at leisure; contract to `[new]` and restart again, which is when the old one stops working. No grace timers, nothing remembered between boots, and **the daemon moves first in both phases** — a caller reloaded onto a token this node does not admit yet cannot refill its certificate cache, which is precisely what a reload makes it do. A single value may simply be swapped on a solo installation, because this surface is off the TLS handshake path and the gap costs only background renewals, OCSP refreshes and first-time issuance, all of which retry. A value that is THERE AND EMPTY is refused rather than read as unset: an unnamed variable expands to exactly that, and minting over it would leave the node admitting a token nothing else on the host has ever seen. Four rules carry the rest. Writes are LAST WRITER WINS, because one object is one write and serializing what PRODUCES a value is the locks' job rather than the store's. A DELETE takes the key AND everything beneath it, because a name in this space is a value and a directory at once. A LIST that matches nothing is a `404` rather than `200 []`, because the consumer's contract needs "no such name" told apart from "a name holding nothing" and this key space cannot store the second. And a LOCK is one record taken with `If-None-Match`, restamped every 5s by the process holding it and takeable by anyone once it has gone 10s unrestamped — the norms of the file-backed storage the same automation ships with, so an installation keeping its certificates in a bucket waits exactly as long as one keeping them on a disk. Acquisition never blocks (the caller polls, every 1s), a restamp that does not land drops the lock rather than assuming it survived, and a release only ever removes the record it was handed — so a holder that lost its lock removes nothing, and is answered `204` all the same, because unlocking is idempotent.
- **The platform domain's own APEX is the fleet's API, and it is ONE switch that is ON.** A platform domain (`dev.example.com`) is the name every `<project>.dev.example.com` hangs off, and nothing ever served it: `*.<domain>` is exactly one label and never the domain itself, so it has no route and — because `/v1/ingress/ask` refused it — no certificate either. `api.public` (`--api-public` / `--no-api-public`, `SCAFO_API_PUBLIC`, `api.public`, written `1`/`true` or `0`/`false` and REFUSED for anything else, exactly as the observability switch is) makes it the installation's front door: `renderRoutes` emits an EXPLICIT route per bare apex to the node's own daemon — the same upstream the wake hosts and the catch-alls take — and any node answers any call there, because the registry is bucket-shared and the API is the same on all of them. So CI, a CLI or a dashboard has ONE well-known name for the fleet, whichever machine the request lands on. ON by default because there is no prior behaviour to preserve, and the switch exists for the operator who wants that name for something else or keeps their API off the internet; off, everything is byte-identical to before it existed. Four rules carry it.
  - **THE APEX MUST NOT REACH `/v1/storage`, AND THE EXCLUSION IS AT THE INGRESS.** That surface carries private keys in both directions behind ONE SHARED TOKEN meant for a local or tunnelled caller (see the bullet above), and a public name in front of it is exactly what its own comment forbids. `/v1/ingress/traefik` goes with it and for the same class of reason: it is unauthenticated because it is a pull-provider endpoint for an ingress inside this node's network namespace, and what it discloses — every host the node serves and the loopback port behind each — is a colocated fact rather than a public API. Both are named ONCE, in `API_DENIED_PREFIXES` (`src/core/placement/routes.ts`), travel to the drivers in `IngressDesired.api.denied`, and are matched at a path SEGMENT boundary — the prefix exactly, or the prefix and `/` and anything — so `/v1/storagex` is a different path in both. Health and the on-demand ask stay reachable: they answer yes or no about names that are already public.
  - **EACH DRIVER ENFORCES IT ITSELF, IN ITS OWN GRAMMAR, AND BOTH FAIL CLOSED.** Caddy gets TWO routes per apex, denial FIRST because it matches in array order: `{host, path: ["/v1/storage", "/v1/storage/*", …]}` answered `404` by `static_response` — Caddy's own answer, dialling nothing — then `{host, not: [{path: [same]}]}` proxying everything else to the daemon. Traefik gets two routers with STATED priorities, because rule length cannot be trusted to rank two rules about the same host and the same paths: ``Host(`apex`) && (Path(`/v1/storage`) || PathPrefix(`/v1/storage/`) || …)`` at `API_DENY_PRIORITY` (3) sent to `noop@internal` — Traefik's own service for a router that must reach no backend, and it must be a service that RESOLVES, since a router naming an unknown one is DISABLED and a disabled denial falls through — above ``Host(`apex`) && !Path(`/v1/storage`) && !PathPrefix(`/v1/storage/`) && …`` at `API_PRIORITY` (2). The negation on the apex router is what makes either half sufficient on its own: a rule the ingress refuses disables that router, and nothing is served rather than everything. Both shapes are PINNED EMPIRICALLY (Caddy 2.11.4, Traefik 3.7.11) and `test/ingress-parity.test.ts` reduces both formats to `host → upstream` pairs CARRYING THEIR PATH SEMANTICS, so a driver that agreed on the hosts and not on the prefixes cannot pass.
  - **PRECEDENCE, IN BOTH DIRECTIONS.** The API entries sit BELOW every route and every wake host — an apex an application already answers on (a custom domain claimed as the platform domain, or a parked environment holding it open) is left out of `api.hosts` entirely, because the first thing to claim a host keeps it — and ABOVE the catch-alls, which matters the moment one platform domain is a subdomain of another (`dev.example.com` under `example.com`): the outer domain's `*.example.com` matches the inner one's apex, and the API must win. In Caddy this is one block re-appended as a unit whenever it is not already exactly right, the same machinery the catch-alls always had; in Traefik it is the stated ranks above.
  - **THE CERTIFICATE AND THE DISPATCH FOLLOW THE SAME SWITCH.** `servesHost` APPROVES the bare apex while `api.public` is on — with no bucket read, because the name is this node's own configuration and what answers there is this very daemon — which is the only way the name is ever issued a certificate; off, it is refused exactly as it always was, since a certificate for a name nothing routes is a public record of an answer that does not exist. And the host-dispatch middleware gives the apex to the API ROUTES rather than to the wake surface (`WakeService.handles` answers false for it), so a path the API does not carry is the API's own `about:blank` 404 rather than "nothing is served at this host". NOTHING IS OPENED: every route keeps the token gating it already had, and the apex is a way IN, never a way AROUND.
- **Observing a node is ONE switch, and it is off.** `observability.enabled` (`--observability`, `SCAFO_OBSERVABILITY`, written `1`/`true` or `0`/`false` — anything else is REFUSED rather than read as off, because a switch silently off is the whole failure mode) turns on exactly two things and nothing else: the daemon emits its own events, and every runtime process this node spawns is given `CELLD_OTEL=1`. The variable is composed where `runtime.celldEnv` is RESOLVED rather than in the driver, as a DEFAULT UNDER the operator's own set — a `runtime.celldEnv` naming `CELLD_OTEL` wins whichever value it holds, `0` included, because the escape hatch is the escape hatch and the node's switch only ever fills a gap. No listener, no route, no bucket write comes with it. **THE SEAM IS THREADED AND THE OFF STATE IS AN ABSENT ONE.** `createObservability` (`src/daemon/observe.ts`) is reached through `DaemonContext.observability` and the executor's deps exactly as the clock and the weighted draw are — never as a global — and every emission site is written `observe?.emit({ ... })`, because optional chaining short-circuits the ARGUMENT too: a node that is not observing never builds an event object, and the seam is only ever attached while the switch says so. What it records goes into a BOUNDED in-memory ring (512, oldest dropped and counted) which the flusher below empties into the bucket. Two things are worth knowing beyond the switch. **A request on the wake surface is named on EVERY answer** — `x-scafo-wake`, a short random id, on the served response, the held-then-`503`, the `404` and the refusal alike, whether or not the node is observing: it costs a few random bytes and it is what ties a caller's failed request, an ingress log line and that request's own events together, and a forwarded answer carries THIS node's id rather than the peer's. **And what a pass cost the bucket is measured with a counting store** (`src/core/registry/counting.ts`) wrapped around the registry THE LOOP uses, and around a held wake's own reads, per-caller in both cases — the counters are monotonic and a shared wrapper would read one caller's work into another's. `reconcile.pass.end` reports round trips and listings apart, because one listing costs a page rather than a trip.
- **The ingress's access log is the only complete account of what a node SERVED, and counting it is a SECOND, separate opt-in.** The daemon sees the requests it wakes and nothing else: once a process is up, traffic goes ingress → process and never touches the node's own surface. So `observability.ingressAccessLog` (`--ingress-access-log`, `SCAFO_INGRESS_ACCESS_LOG`) names the FILE an operator's ingress writes its JSON access log to, and the node follows it. **OPT-IN BY PRESENCE, WITH NO DEFAULT AND NO WARNING FOR NOT HAVING ONE** — most operators run their ingress their own way, and an installation that does simply never names this: absent, no adapter is built, nothing is said past one boot line stating that counters are off. **Named while `observability.enabled` is off it is REFUSED at config time**, naming both settings and the way forward, because a file nothing would ever open is an operator who believes they are counting requests and is not — the same silent-off failure the switch above refuses, one layer out. **ONE TAILER, TWO PARSERS, DETECTED PER LINE.** The parsers are PURE and live in core (`src/core/utils/access-log.ts`) so they are testable without a filesystem; the tailer is a DRIVER (`src/drivers/observe/access-log.ts`) because only a driver may reach for `node:*`. Caddy's `json` access log gives `request.host`, `request.method`, `status`, `size` and `duration` (SECONDS, float); Traefik's `--accesslog.format=json` gives `RequestHost`, `RequestMethod`, `DownstreamStatus`, `DownstreamContentSize` and `Duration` (NANOSECONDS) — both verified against a Caddy 2.11.4 and a Traefik 3.7.11 writing their own logs, which is also how it was found that **Caddy's `request.host` carries the port** when the client sent one and Traefik's does not, so both are normalized the same way. Detection is a look at two keys per line rather than once per file, because a rotated or concatenated file carrying both formats must not be able to wedge the reader. **NOTHING THROWS AND NOTHING IS DROPPED SILENTLY:** a line of no format, or one carrying no host and status, increments a `malformed` counter and is skipped — so a node pointed at Caddy's RUNTIME log instead of its access log shows a malformed count that tracks its line count, rather than reporting zero traffic. **THE TAILER STARTS AT THE FILE'S CURRENT END AND FOLLOWS ROTATION**, which is the trap: history belongs to whoever already served it, and re-counting it on every restart would invent traffic. It polls `stat` (rather than `fs.watch`, which reports a rename on a path it is no longer watching and is unreliable on bind mounts and network volumes), and it handles both shapes a roll takes — a RENAME plus a fresh file, where the file that was rolled away is DRAINED TO ITS END before the new one is opened, and a TRUNCATION in place. Partial lines are buffered until their newline; a line past `DEFAULT_MAX_LINE_BYTES` is given up rather than grown into, so no writer can take the node's memory with it. **ATTRIBUTION IS THE ROUTING, NEVER A SECOND READING OF IT.** `applyIngress` hands `createIngressCounters` the very `IngressDesired` it hands the ingress, plus the custom-domain claims — so a custom domain, and which environment a build's own hash host is a leg of, are answered by the one thing that knows, and a canary's two legs add up to their environment. A host the routing does not name falls to the PURE platform host grammar (`src/core/placement/hosts.ts`, extracted from the wake surface's own resolution so the two can never drift): `<project>.<domain>` as `production`, `<project>--<ref>.<domain>` as that ref, which is what a PARKED or STARTING environment's traffic looks like. Anything else lands in an `unattributed` bucket keyed `-`, which is not a slug and can therefore never collide with a real name. What is kept per `{project, env}`: requests, bytes, the four status classes plus `other`, and seven fixed duration bands (10/50/100/300/1000/3000ms and past); fixed rather than configurable, because bands that differ per node cannot be added up across a fleet. It is MONOTONIC on the same terms as the ring — `snapshot()` reads without consuming or resetting, a reader wanting a window subtracts two — and the flusher below is what puts those snapshots in the bucket for a reader to subtract. Both examples carry the one documented line that turns the matching ingress's log on (`examples/caddy.json`'s `logging.logs.scafo` plus the server's `default_logger_name`, with `"mode": "0644"` so a node running as uid 10001 can read what Caddy writes as root; the k8s Traefik sidecar's `accessLog` block), commented as optional and as something to skip outright when the ingress is yours.
- **What a node observes ends up in the bucket, in ITS OWN prefix, as compressed Parquet it also throws away again.** The ring and the counters are memory; `createObserveFlusher` (`src/daemon/observe-flush.ts`) is what makes them a record. It is started beside the storage service's loop while `observability.enabled` is on, its timer is unref'd like every other loop on the node, and it is the FIRST loop stopped on shutdown with ONE final flush after the access log has been read to its end — so the last thing written is the whole of what the node saw, the shutdown included. Five things carry it.
  - **THE DRAIN IS A HIGH-WATER MARK, AND THERE MAY ONLY BE ONE DRAINER.** `snapshot()` is unchanged and still reads WITHOUT consuming — it is a window on the recent past and any number of callers share it — while `Observability.drain()` takes everything since the last drain and moves a mark past it. A second drainer would take half the events each and neither would know, which is why the daemon builds exactly one flusher. `drain()` reports what fell out of the ring BEFORE it could be read, SINCE THE LAST DRAIN (`snapshot().dropped` is still the total since the seam was made — two different numbers answering two different questions), and that per-flush loss is written into the file rather than kept as a total, because a total would be counted again on every flush. The ring is drained every `OBSERVE_DRAIN_INTERVAL_MS` (5s) rather than only at flush time, and that is not a second cadence: 512 events is less than a busy node emits in a minute, so draining often is what stops the ring overflowing while it waits for a flush.
  - **KEY LAYOUT, NODE-SCOPED, AND THE SCOPE IS THE WRITE RULE.** `_scafo/observe/<nodeId>/<YYYY>/<MM>/<DD>/<HH>/<epochMs>-<seq>.<ext>`, every segment UTC and every timestamp from the injectable clock. A node writes only under its own segment and sweeps only its own segment, so no node can delete another's history; below that the path is the calendar, so the keys sort in write order and a reader skips whole hours by name. `seq` is the flush's number since that node booted, zero-padded, and it is what keeps two flushes of the same millisecond apart. `observeKey`/`parseObserveKey` live in `src/core/registry/paths.ts` with every other bucket key, and the parse checks the calendar segments AGAINST the timestamp — a key whose path and stamp disagree is not ours and a sweep leaves it alone.
  - **ONE FILE PER FLUSH, THREE RECORD KINDS, ONE `record` DISCRIMINANT.** A `flush` header (what the file carries, what the ring dropped, what the pending buffer dropped, and the adapter's own `lines`/`malformed`/`unattributed`), one `event` per observed moment with the event FLATTENED so a line is one row, and one `counters` per `{project, env}`. SAME FILE rather than sibling keys because a flush is one decision and must land as one write: a bucket charges per request, and two objects can land half of themselves — leaving a window where a node's events exist and its counters do not, which is the one disagreement a reader cannot recover from. The discriminant is `record` rather than `kind` or `type` because an event already carries both. **COUNTER RECORDS ARE MONOTONIC TOTALS SINCE THAT NODE'S BOOT, NOT WINDOWS** — `since` is stamped on each one, and a window is derived AT READ TIME by subtracting two snapshots of the same node, the same `{project, env}` and the same `since`. A node with nothing new to say writes NO OBJECT AT ALL: no events, nothing dropped, and a counters snapshot identical to the last one flushed means an idle node stops writing an object a minute forever.
  - **THE BYTES GO THROUGH EXACTLY ONE SEAM, AND THERE IS ONE CODEC BEHIND IT.** `ObserveCodec` — `extension`, `encode(records) -> {bytes, extension}`, `decode(bytes) -> {records, malformed}` — is declared in `src/daemon/observe-records.ts`; `PARQUET_CODEC` is the implementation and lives next door in `src/daemon/observe-parquet.ts`, because it carries a schema dense enough to need its own header. The flusher puts at the key the `extension` names and a reader picks its codec by the extension it read OFF the key, so swapping the encoding would still be one object plus its extension and nothing else; a file in an encoding the CLI does not know is counted and reported rather than failed over, and so is one whose BYTES are not what its name promised. **THE STORE TAKES BYTES AND ANSWERS THEM, which is the one thing beyond the seam a columnar codec changed.** `CasStore.put(key, body: string | Uint8Array)` and `CasStore.getBytes(key)`: every record the registry keeps is still text and still goes through `get`, which is where the ETag a conditional write needs comes from; an observation flush is never conditioned on anything and would be destroyed by that read's UTF-8 decode, so it is written and read as bytes and nothing needs both. `MemoryCasStore` holds what it was given verbatim, and `uns3` sends `application/octet-stream` for a byte body rather than claiming JSON for it. Without this a `.parquet` object would come back out of a `TextDecoder` full of replacement characters and stop being a Parquet file.
  - **THE ENCODING IS ONE WIDE FLAT TABLE, ZSTD COMPRESSED, AND IT ROUND-TRIPS.** `PARQUET_CODEC` (`extension: "parquet"`) is [`tavolato`](https://github.com/sandros94/tavolato) — a Parquet writer and reader that imports nothing and handles flat schemas of `string`/`json`/`f64`/`f32`/`i64`/`i32`/`bool`/`timestamp`. Three record kinds share a file, and Parquet has one schema per file, so they share a SCHEMA: every field of every kind is a column, only the four each record carries (`v`, `record`, `node`, `at`) are REQUIRED, and everything else is a real Parquet `OPTIONAL` — a `wake.kicked` row is six values and thirty-eight nulls, which is what a columnar format is cheap at. `record` is what a query filters on. **THE TWO NESTED FIELDS ARE FLATTENED BY THEIR OWN PATH**: a counters record's `status` object becomes `status_2xx`/`status_3xx`/`status_4xx`/`status_5xx`/`status_other` (via `STATUS_COLUMN_OF`, a `Record` over the class names so a class added to `StatusClassCounts` stops the build), and its `durations` array becomes one column per band NAMED AFTER THE BAND'S BOUNDARY — `durations_le_10ms` … `durations_le_3000ms` and `durations_gt_3000ms`, derived from `DURATION_BANDS_MS` so a band added to the histogram adds a column and cannot drift from it, and carrying the same semantics the positional array does. The bare `status` column is an i64 and is a `wake.served`'s HTTP status: two fields share that name in the record union and only one of them nests. No JSON catch-all is needed because THE UNION IS CLOSED AND THE BUILD PROVES IT — `COLUMN_OF` is a `Record` over the record union's own keys, so a field added to any `ObservedEvent` variant is a missing property and the build stops rather than the flush silently dropping a column. **AND THE READ SIDE IS THAT MAP INVERTED**, derived from `COLUMN_OF` rather than written down beside it, so the two directions cannot describe different tables: `observeRecordOf` puts back the three things a columnar file changes — an `i64` reads as a `bigint`, a `timestamp` as a `Date`, and the flattened fields have to be gathered up again — validates only the discriminant, the node and the instant, and SKIPS a column this build has no field for exactly as the write side drops a field it has no column for. A row that is not a record is counted into `malformed` and skipped; bytes that are not a Parquet file throw, and `readObservations` is what turns that back into one unreadable key. **EVERY DATA PAGE IS A ZSTD FRAME** (`OBSERVE_PARQUET_WRITER_CODEC` / `OBSERVE_PARQUET_READER_CODECS`, `node:zlib`'s `zstdCompressSync`/`zstdDecompressSync`). Sync on both sides ON PURPOSE: `tavolato` defers only when the codec it was given does, so a synchronous codec is what keeps `ObserveCodec` a synchronous seam — the one `as SyncParquetWriter` in `encode` is that fact asserted once. The compression is stamped per column chunk, so nothing reading these has to be told about it; measured on a 2000-record flush it is 7.9 KB against 149 KB uncompressed, which is what a wide table of repeated node ids, repeated record kinds and mostly-null columns compresses to. The dependency is pinned to a pkg.pr.new preview build (`https://pkg.pr.new/sandros94/tavolato@<commit>`) and **moves to an ordinary semver range once `tavolato` has its first npm release**. The test suite pins the schema and every record kind's row, round-trips all three kinds through the codec itself, and — where a `duckdb` binary is on the machine, skipped when it is not — reads a real encode back with the DuckDB CLI, which is the only check that says the bytes are Parquet rather than that the library agrees with itself.
  - **A FLUSH THAT DOES NOT LAND KEEPS ITS EVENTS, BOUNDED, AND RETRIES ON THE FLUSH CADENCE.** Flushes go out every `OBSERVE_FLUSH_INTERVAL_MS` (60s) or as soon as the pending buffer crosses `OBSERVE_FLUSH_MAX_RECORDS` (2000), whichever comes first; the constants are constants and the config surface does not grow for them. A failed put keeps the drained events for the next attempt at the FLUSH cadence rather than the drain one — a bucket that is down must not be retried every five seconds — and the buffer is bounded at `OBSERVE_PENDING_MAX_RECORDS` (20 000), past which the OLDEST are dropped and counted into the next header, because a node whose bucket never comes back must not fill its memory with what it cannot write. Counters are NOT retried: they are monotonic, so the next snapshot supersedes the lost one and only the sample resolution is gone. **RETENTION IS A SLOW SWEEP OF THIS NODE'S OWN PREFIX**: every `OBSERVE_SWEEP_EVERY_FLUSHES` (60, so about hourly) it lists `_scafo/observe/<nodeId>/`, deletes per key what is older than `OBSERVE_RETENTION_DAYS` (30), and stops at `OBSERVE_SWEEP_MAX_DELETES` (500) with the rest going next sweep. It sweeps on the FIRST flush too, so a node back from a long stop cleans up without waiting an hour, and it never throws — retention is housekeeping, and a sweep that could not run costs disk rather than correctness.
- **Reading it back is two commands, and they read the BUCKET.** `scafo metrics [--project X] [--env Y] [--since <ISO|1h>] [--json]` and `scafo traces [--wake <id>] [--project X] [--since ...] [--limit N] [--all] [--json]` take the same `SCAFO_S3_*` configuration `scafo trust` and `scafo varset` do, and no node is asked: the records were flushed by whichever nodes were running at the time, and those nodes may well be gone. `--since` is a duration back from now (`90s`, `15m`, `1h`, `7d`) or an ISO-8601 instant, and anything else is REFUSED rather than silently defaulted, because a window that quietly became the default reads exactly like an empty one. Three rules are worth knowing. **THE FILE FILTER HAS SLACK BELOW THE WINDOW AND NONE ABOVE IT** (`OBSERVE_READ_SLACK_MS`, 15 minutes): a file is written when its records are flushed, so a retried flush is much NEWER than what it carries and is never meaningfully older — records are then filtered exactly, by their own `at`. **A WINDOW IS FIRST-VS-LAST PER NODE, PER `{project, env}` AND PER RUN**, a run being one unbroken `since`; a run that BEGAN inside the window is taken whole rather than differenced, which is what makes a node restarting mid-window report its traffic instead of a negative number, and a window holding one snapshot of an older run reads as zero because there is nothing in it to subtract from. The latency columns are BANDS (`<=50ms`, `>3s`) rather than interpolated percentiles, because bands are what was counted. **NOTHING FOUND IS AN ANSWER AND IT NAMES THE SWITCH**: no node has ever written (is `observability.enabled` on?), nodes wrote but not in this window (widen `--since`, and the nodes are listed), or the nodes report on themselves and simply count nothing (`observability.ingressAccessLog` is the second opt-in). Objects are read through `CasStore.getBytes` and decoded through the codec seam — a row that is not a record is skipped and counted, a whole file that will not decode is reported as unreadable and the rest of the window still answers, never thrown over — and `--wake` is never truncated by `--limit` — half a request's steps read as a request that stopped there, which is the failure being looked for. **`scafo traces` LEAVES THE RECONCILE LOOP'S OWN PASSES OUT UNLESS `--all` ASKS FOR THEM.** Every node emits `reconcile.pass.start` and `reconcile.pass.end` every 5s whether or not anything happened — nothing else in the catalog is periodic — so they are also the NEWEST events in any window, and a default listing of 200 was several minutes of a fleet doing nothing with the deploys, wakes, rollouts and gates a reader came for pushed out beneath them. They are taken out BEFORE the limit rather than after (`PERIODIC_EVENTS`, `src/cli/_traces.ts`), which is the whole of the fix: counting them against it would spend the window on them either way. Nothing is dropped silently — how many were held back is always printed, and a window holding nothing else says so in its own words rather than as "nothing recorded". **AND `scafo metrics` CHECKS THE NAMES IT WAS GIVEN BEFORE IT PRINTS THEM.** The counting node attributes a host through the routing it published and falls back to the PURE platform host grammar for everything the routing does not name, which cannot tell a build id from an environment name nor a real project from a label a crawler invented — so a build's own hash host arrived as `ENV = <build id>` and any `*.<domain>` junk became a project row of that name. The reader has a registry and the writer does not, so it is the reader that resolves: one listing for the projects, then one of environments and one of builds PER PROJECT THE WINDOW ACTUALLY NAMED (`readMetricsNaming`, `src/cli/_metrics-names.ts` — listings only, never a record read). A build's host is then shown under its project as `(build <short hash>)` rather than folded into the environment it was deployed into, because that would cost a read per build id while the listing already proves what it is; the ROUTED case was always attributed to the environment by the routing and is untouched. Anything the registry does not hold — an invented project, a real project's unknown ref, and the node's own `-` bucket alike — is ONE `(unmatched)` row, parenthesised so it can never collide with a slug. A name deleted since it was counted reads as unmatched too, which is the honest answer: deleted from the bucket means gone.
- **Two ways in, one way out.** The deploy-facing routes accept either an operator's node token or a project's workload OIDC token. The node token is tried first because it needs nothing but the header; only when it fails as authentication is the bearer offered to the trust policy of the project the request names. A caller that fails both gets the single `auth-invalid` problem document every other rejection uses — it cannot learn which half it failed, nor whether the project exists. The one distinguishable outcome is `trust-mismatch`, which is authorization: a token trusted for one project can never deploy or flip another.

## Packaging

- **The image is the node, whole.** `Dockerfile` at the repository root builds it: `docker build -t scafo .`. Multi-stage — a `node:24-slim` build stage installs with pnpm, runs `pnpm build`, prunes to production dependencies and resolves esbuild's per-platform binary; the final stage is `node:24-slim` plus `ca-certificates` (the slim images ship no root store and the bucket is reached over TLS), celld copied out of `ghcr.io/denoland/celld:0.3.0`, that esbuild at `/usr/local/bin/esbuild` with `ESBUILD_BINARY_PATH` pinned to it, `dist/` and the production `node_modules` at `/app`, and a non-root `scafo` user (uid 10001) owning `/var/lib/scafo`, which `SCAFO_STATE_DIR` names. `ENTRYPOINT` is the CLI and `CMD` is `sail`, so `docker run scafo sail --listen 0.0.0.0:7400` is the whole invocation. **celld is pinned by DIGEST as well as by tag** — it runs every customer's code and holds every cell's replication chain, so the bytes must be the ones that were tested; nothing else in the file is pinned that way. `.dockerignore` denies everything and re-includes only the manifest, the lockfile, the workspace file, `tsconfig.json`, `build.config.ts` and `src/`, so a host `node_modules` or a stale `dist/` cannot reach the build.
- **THE STOP GRACE IS PART OF THE PACKAGING, AND IT IS AT LEAST 35 SECONDS.** On SIGTERM the daemon writes `drainingAt` so placement stops giving it work, releases the coordinator lease, stops reconciling, closes its listener, and only THEN stops the celld processes it supervises — each of which drains in-flight requests for 25s (`CELLD_SHUTDOWN_DRAIN_MS`, derived from the driver's 30s stop grace less its 5s headroom) and is killed at 30s. Docker's default of 10s and Kubernetes' of 30 both cut that off mid-drain: requests are dropped in flight, the container exits 137, and the fleet has to time the node out over the liveness window instead of being told it left. So `stop_grace_period: 35s`, `terminationGracePeriodSeconds: 35`, `docker stop -t 35` — the image says so in a comment beside `STOPSIGNAL SIGTERM`, both examples carry it, and `test/integration/e2e-image.test.ts` asserts the exit code is 0.
- **The ingress shares the node's network namespace, and that is the whole topology.** Runtime processes bind `127.0.0.1` and nothing else, so whatever routes to them must be on the same loopback: `network_mode: "service:node"` in compose, a sidecar container in the same pod on Kubernetes, which is the same arrangement for free. Caddy is PUSHED (the node calls its admin API on that loopback, so it needs `ingress.adminUrl` and a server it can write into); Traefik PULLS (the sidecar polls `http://127.0.0.1:7400/v1/ingress/traefik`, so the node needs no address for it at all — only `ingress.entryPoints`, naming which of Traefik's entryPoints the published routers attach to, because routers naming none attach to all of them).
- **The binary is the same `dist/`, sealed — and it is compiled FROM the build, never from `src/`.** `scripts/compile.sh` (`pnpm compile`) runs `pnpm build` and then `deno compile` over `dist/cli/index.mjs`, producing `build/scafo-<os>-<arch>` and a `.sha256` beside each; `linux-amd64` and `linux-arm64` are the default targets, and the arm64 one cross-compiles cleanly from an amd64 host. Compiling `dist/` rather than the sources is the load-bearing choice: `dist/` is what the tests, the image and npm all run, and a second build of the same project would drift from it silently. **IT COMPILES OUT OF A STAGING DIRECTORY (`build/.stage/`) AND MUST**: Deno resolves npm packages through `node_modules` when it finds one, so compiling from the repository root embeds the whole development tree — 299MB against 113MB — esbuild's native binaries included. The staging directory holds the built `dist/`, a THREE-FIELD `package.json` (the CLI reads its version out of `../../package.json`, and a copy of the real one would carry `dependencies` for Deno to resolve), and a generated import map of every runtime dependency AT THE VERSION `node_modules` ACTUALLY HAS, so the map can never drift from the lockfile. `esbuild` is excluded from that map by name — it is a runtime dependency of the project but the binary only ever hands its PATH to `celld deploy`, and resolving the package would put a toolchain inside every copy. Two consequences to know: `ESBUILD_BINARY_PATH` is the ONLY way a node running the binary finds a builder, and **a module reached through `createRequire` is invisible to `deno compile`** — which is why `tar` is loaded with a literal `await import("tar")` (see `src/drivers/archive/tar-zst.ts`), the one form a bundler and Deno can both follow.
- **The permission set is baked in at compile time, and what it DENIES is the point.** `deno compile` seals permissions into the binary: what is not granted there can never be granted later. The binary gets `--allow-env --allow-read --allow-write --allow-net --allow-sys --allow-run` and NOT `-A`, because two things can be denied without denying a feature — `--allow-ffi` (no dependency loads a native library, and dlopen is a way around every other line) and `--allow-import` (the module graph is sealed; nothing is fetched and evaluated at runtime). The other six are unbounded BY THE PRODUCT rather than by laziness: every path and every address they cover is named in configuration an operator writes — the state directory anywhere `SCAFO_STATE_DIR` says, the config file, the varset key, the ingress access log, the directory `scafo deploy` packs, the bucket endpoint, another node's API, Caddy's admin, any OIDC issuer a project trusts, and `celld` wherever `runtime.celldBin` names it. `--allow-env` is the one that could be enumerated (~60 names) and deliberately is not: the list would have to cover whatever the h3/srvx/tar/uns3 tree reads for itself, and a name missing from it is not a denied read but an uncatchable `NotCapable` that kills the daemon on whichever host first sets it.
- **`scripts/install.sh` is the bare-metal path, and it verifies everything it installs.** A POSIX-sh bootstrap for one Linux host (amd64/arm64, glibc — musl is refused loudly, with the image named as the way out): it downloads the four executables a node is made of — `scafo`, `celld`, `caddy` and `esbuild`, the last of these because `celld deploy` bundles every artifact with it and a node without one accepts deploys and then fails all of them — checks each against a sha256, and only then installs any of them. **VERIFY-ALL-THEN-INSTALL, and that ordering is the contract**: a run that gave up halfway would leave a new `scafo` beside an old `celld`, two versions nothing ever tested together. celld, upstream Caddy and esbuild are pinned by version and checksum in the script itself (`SCAFO_INSTALL_MIRROR` may move where they are fetched FROM, never what they must be); the two binaries out of this project's own releases cannot be, because both come from a `latest` URL a constant could only go stale against — `scafo` from `SCAFO_INSTALL_BASE` and `scafo-caddy` from `SCAFO_CADDY_BASE`, each held to `SCAFO_SHA256`/`SCAFO_CADDY_SHA256` or, failing that, to the `.sha256` published beside it, which catches corruption and is said out loud to prove nothing more. Under root with systemd it writes `scafo-node.service` and `caddy.service`, creates `/var/lib/scafo` `0700` owned by a `scafo` system user, and writes `/etc/scafo/node.env` (`0600`) and `/etc/scafo/caddy.json`; otherwise it prints the same commands to run by hand. **Two directives in the unit are load-bearing.** `KillMode=mixed`, because systemd's default signals every process in the cgroup at once — which would SIGTERM the runtimes beside the daemon instead of letting the daemon stop them in its own order — and `TimeoutStopSec=40s`, which is the 35-second rule above. **THE INGRESS IS scafo-caddy BY DEFAULT** — Caddy built with the `caddy.storage.scafo` module, which keeps the certificates, their keys and the ACME account IN THE BUCKET and reaches them through this node's `/v1/storage`, so a fleet serves one certificate instead of each node issuing its own for the same names. `SCAFO_INSTALL_CADDY=plain` opts down to upstream Caddy with a config carrying no `storage` block, byte for byte what the script wrote before the flavour existed. **Both are installed AS `caddy`**, which is what keeps the unit, the `BINARIES` list and every line of `uninstall.sh` free of the question; the manifest's `caddy_flavor=` records which it was, for the REPORT only — under plain Caddy `--purge` takes the certificates with `/var/lib/caddy`, under scafo-caddy they were never on that host and no flag reaches them, and the uninstall says so. **THE TOKEN IS A systemd CREDENTIAL, AND THAT IS THE WHOLE PERMISSION STORY.** The node mints `/var/lib/scafo/storage-token` `0600` as `scafo` inside a `0700` directory; the ingress runs as `caddy` and cannot read it, and neither mode is loosened, because that surface carries private keys in both directions. `LoadCredential=storage-token:/var/lib/scafo/storage-token` has the service manager read it as root and place a `r--------` copy in `$CREDENTIALS_DIRECTORY` that only the service's own UID may open, and `caddy.json`'s `token_file` is `{env.CREDENTIALS_DIRECTORY}/storage-token` — resolved by the module's own `Provision()`, which runs Caddy's `ReplaceKnown` over both fields. **The first boot is a race the ingress loses on purpose**: `After=scafo-node.service` only means the node's process was exec'd, the token appears a moment later, and a `LoadCredential=` whose source is missing is FATAL — the start fails at `243/CREDENTIALS` _before any of the unit's own commands run_, so an `ExecStartPre` wait loop cannot help, because it would be the command that fails (verified empirically on systemd 255). What survives it is `Restart=on-failure` plus `StartLimitIntervalSec=0`, which turns off the rate limiter that would otherwise give up after five starts and leave the ingress dead over a gap that lasts seconds. `Requires=` is deliberately NOT set: a running Caddy is unaffected by the node stopping, and binding them would take TLS down on every node restart. It starts nothing: a node cannot boot without a bucket, and those credentials are the operator's to write. **Its honest limits are stated in the script and printed at the end of every run**: there is no scafo-caddy release yet, so the default path 404s today and fails with a message naming `SCAFO_INSTALL_CADDY=plain` and `SCAFO_CADDY_BASE` as the two ways forward; and wireguard-tools is a package-manager job, because a tunnel needs a kernel module and NET_ADMIN, so the hint is printed rather than acted on.
- **`scripts/uninstall.sh` is its inverse, and the two are ONE LIST IN TWO FILES.** It stops the ingress first and the node second — the reverse of the order the units are written in, so nothing is routed to processes that are about to stop — waits out the node's full 40s drain, then disables and removes both units (`daemon-reload`, and the `multi-user.target.wants` symlinks by hand, for a host whose systemd is not running), the four executables from the directory the install used, and `/etc/scafo`. **IT KEEPS `/var/lib/scafo` UNLESS `--purge` SAYS OTHERWISE, and that default is the whole design**: the state directory holds the Ed25519 pair this node's registry record names and the storage token the ingress presents to `/v1/storage`, and NOTHING CAN REISSUE THEM — reinstalling over what is kept brings the node back as itself, purging brings back a different one. `--purge` additionally takes Caddy's certificates and ACME account (`/var/lib/caddy`), the ingress log directory and the system accounts; `--dry-run` prints every removal and performs none, and is the one mode allowed to run unprivileged over a root-owned install, because it changes nothing. **NEITHER SCRIPT TOUCHES THE BUCKET.** The registry is the fleet's: deletion in it is gated on a coordinator lease an uninstall does not hold, another node may be serving those environments, and a node that stops needs no cleanup anyway — it writes `drainingAt` on the way out and placement counts it out on the coordinator's next pass, or after the liveness window if it never got to say so. **The link between the two scripts is `install.sh`'s `write_manifest()`**, which records into `/var/lib/scafo/install.manifest` the two facts nothing else on the host carries — which bin directory the executables went to, and which of the two system accounts that run CREATED rather than found, because deleting a `caddy` a distribution's package made is a far worse mistake than leaving an unused account behind — plus `caddy_flavor=`, which changes nothing about what is removed and everything about what `--purge` means. The manifest is NOT a dependency: without one the uninstall derives the bin directory from the unit's `ExecStart` and then from PATH, and removes the `scafo` account only when its home is the state directory install.sh gave it, never `caddy`, printing the command instead. Running it twice, or on a host where the installer half-ran or never ran, succeeds quietly.
- **`examples/` is where the operational knowledge lives in-repo, and it is usage-facing.** `examples/compose.yaml` plus `examples/caddy.json` is a runnable single-host stack — a bucket, one node built from the Dockerfile, and Caddy in its namespace — mirroring the topology the end-to-end suites validate. `examples/kubernetes/node.yaml` is the same node as a Deployment of two, with a Traefik sidecar, `SCAFO_ADVERTISE` from the pod IP through the downward API, and state on an `emptyDir` because node identity is disposable by design: a replaced pod registers a fresh one and the registry in the bucket is the truth, so a PVC is an optimisation rather than a requirement. `examples/kubernetes/README.md` carries the apply order, how traffic reaches the sidecars, and the two rules that must not be violated — the grace above, and that one bucket-and-prefix is one fleet. Keep every example self-contained: no references to plans, waves or conversations, and nothing a reader has to look elsewhere to understand.

## Code Conventions

- Use **ESM** and modern JavaScript, with a type-first approach.
- Before adding new code, study surrounding patterns, naming conventions, and architectural decisions.
- `isolatedDeclarations` is on: every exported symbol needs an explicit type annotation.
- Relative imports carry the explicit `.ts` extension.
- Prefer **Web APIs** over Node.js APIs where possible.
- Keep runtime code minimal and fast.
- Place non-exported/internal helpers at the end of the file.
- Comments are usage-facing only — what a caller must know, constraints, caveats. No development history or decision narrative. `TODO` comments are fine for known gaps.
- Split logic across files; avoid long single-file modules (>200 LoC). Use `_*` prefix for internal files.
- For multi-arg functions, use an options object as the second parameter.

Project specs and the decision log are maintained outside this repository.

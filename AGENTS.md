# scafo - Agent Guide

`scafo` is a self-hosted, multi-tenant serverless deployment platform for JS apps. Its JSON registry lives in an S3-compatible bucket and is mutated with CAS conditional writes; it has no database or consensus protocol. One binary is both node daemon and CLI.

## Ask first

Ask before acting when intent is ambiguous. For design or product decisions, run a short structured Q&A: numbered questions, 2–4 concrete labeled options, a marked recommendation, then synthesize and confirm decisions before implementation.

## Boundaries

- A Scafo fleet is one installation: one registry and its Scafo nodes. A Scafo node is a machine running `scafo sail`.
- The unit scafo deploys, places, serves, blocks, retires and deletes is an **application**, identified by its **name**: a slug of 1-63 lowercase alphanumerics separated by single hyphens, the same rule Celld applies to a config's `name`. One application is one Celld fleet and one current deployment, and it is served at `<name>.<platform domain>`. A Scafo node may supervise one Celld node process per assigned application. Unqualified `fleet` and `node` mean Scafo's machine-level concepts; name Celld's process-level concepts explicitly.
- Scafo requires Celld 0.5.0: `scafo sail` runs `celld --version` before it opens the bucket and refuses an older or unreadable binary with `capability-missing`, and each node record carries the `versions` (Scafo and Celld) its daemon booted with. A node does not start an application's process, and does not accept a deploy for it, while another live node serving that application reports a different Celld version (`version-skew`, 409); an upgrade freezes deploys first, then stops every node of the installation. Celld owns deployment adoption, application health, cells, and runtime resource policy; Scafo owns registry, auth, placement, supervision, deploy intake, and the routing every ingress reads.
- Celld exposes one current deployment per application fleet. Scafo records a monotonic deployment revision, not a selected version; it has no per-deployment host or local version selection. See https://github.com/denoland/celld/issues/181.
- Vocabulary follows Celld: a **deployment** is what Celld serves, identified by its **version**; a **deploy** is one run of `scafo deploy`; a **build** is compiling only (esbuild, the image, `pnpm build`).
- `/.well-known/scafo/health` is served by the node/API listener; `/.well-known/celld/health` is served on application hosts. `scafo health` probes the former at the listener it resolves from the daemon's own sources (env and config file, not `sail` flags); it is the image's HEALTHCHECK.

## Commands

- `pnpm build`, `pnpm compile [linux-amd64|linux-arm64]`, `pnpm test`
- `pnpm vitest run test/utils.test.ts`, `pnpm typecheck`, `pnpm lint`, `pnpm fmt`
- `node dist/cli/index.mjs sail --help`

The ordinary integration suite starts an S3 store with testcontainers. Set `SCAFO_TEST_STORE=seaweedfs|rustfs`, or supply `S3_ENDPOINT`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, and `S3_BUCKET`.

Docker E2E is opt-in; absent Docker skips a suite, not a product failure. A run builds `dist/` once, before any suite starts (`test/integration/_global-setup.ts`); no suite builds for itself and every node container bind-mounts the worktree read-only, so several suites may share one command and run in parallel. Run `docker build --target probe -t scafo-probe .` once (the node host the suites mount the build into). Use `vitest.no-store.config.ts`; these suites own their containers.

- `SCAFO_E2E=1 pnpm vitest run --config vitest.no-store.config.ts test/integration/e2e.test.ts` — Caddy, deploy adoption, OIDC, retirement.
- `SCAFO_E2E=1 pnpm vitest run --config vitest.no-store.config.ts test/integration/e2e-traefik.test.ts` — Traefik pull provider.
- `SCAFO_E2E=1 pnpm vitest run --config vitest.no-store.config.ts test/integration/e2e-multinode.test.ts` — replicas, selectors, durable cells, failover, drain, reassignment.
- `SCAFO_E2E=1 pnpm vitest run --config vitest.no-store.config.ts test/integration/e2e-image.test.ts` — non-root image, bundled tools, healthcheck, shutdown.
- `SCAFO_E2E=1 pnpm vitest run --config vitest.no-store.config.ts test/integration/e2e-tls.test.ts` — TLS storage, locks, and auth.

- `pnpm vitest run test/integration/store.test.ts` — bucket conformance against the `SCAFO_TEST_STORE` matrix (seaweedfs, rustfs).

## Placement of work

- `src/core/**` holds runtime-agnostic contracts, registry, auth, and pure placement logic.
- `src/drivers/**` implements runtime seams; `src/daemon/**` and `src/cli/**` assemble them.
- Internal files use a leading `_`. `examples/` is production-shaped; `playgrounds/` is disposable. Keep both executable and self-contained.

## Architecture and security

- All registry mutation uses `CasStore` preconditions. Surface conflicts as `ScafoError("cas-conflict")`; retrying callers re-read before writing. The store driver repeats a write the store answers with a transient error and raises `ScafoError("store-unavailable")`—503—once the tries run out, and a lease or lock refused by its own precondition is re-read before it is called lost.
- Keep core pure where practical and on Web APIs; `unjwt` in `core/auth` and `unsecure` where external text is parsed are the exceptions. Put runtime work behind core interfaces in drivers; add external runtime dependencies to `build.config.ts`.
- Token failures—bad, expired, forged, replayed, or unknown-key—are `ScafoError("auth-invalid")`. `trust-mismatch` remains the distinct authorization refusal. Its detail echoes only what the token itself said and ends with the `scafo trust add` command that admits exactly that subject — never the subjects already trusted, which any workload of a shared issuer could otherwise read, and no command at all for a subject carrying a glob, a quote or whitespace. `scafo trust set` states an issuer's whole subject list, `scafo trust add` keeps it and appends, each `--subject` is one subject (the flag repeats; nothing is split on commas), and every edit of a policy is a CAS update of the policy as stored.
- External text becomes an object through `unsecure` only—registry documents, request bodies, tokens, access logs, config and artifact files carry no key an object answers for on its own, and a config setting is read from a key the file itself holds. One rule refuses those names wherever variables are written: `scafo deploy --var` and `runtime.celldEnv` alike.
- Operators and nodes use separate keyspaces and cannot share an id. Admin and operator roles differ; operator-tier keys are application-scoped: a scope entry is `*` (all), an exact name, or a PREFIX GLOB — a run of name characters, which may end in a hyphen, followed by one trailing `*`, so `shop-*` reaches `shop-preview` and not `shop`. `*` anywhere else is `invalid-input`. A missing scope grants nothing. Bucket credentials remain fleet-root authority.
- Placement is selectors, rendezvous hashing, then replica count. Scafo neither infers nor reserves host resources; operators set runtime policy through Celld and the host/container platform via `runtime.celldEnv`, `--celld-env`, or `SCAFO_CELLD_ENV`. Scafo adds no Celld policy defaults.
- Bound deploy intake by archive size and entries, output tail, active/queued tasks, staged bytes, and receive/queue/task deadlines. These are scheduling bounds, not runtime admission.
- A deploy id is `<application>.<16 hex>`, and every state it moves through is a registry record under that application: any node answers a poll—the application in the id is what authenticates the caller—and a restart of the accepting node loses nothing. A record that reaches `deployed` names the deployment it produced by version, a failed record keeps the code of the error that failed it, and the CLI exits with it. A `celld deploy` that ends badly is `publish-failed` (502) with Celld's own output as the detail, whatever the cause; `invalid-input` is what Scafo itself refused before publishing. A failure with no code of Scafo's is the node's own `internal` (500) — in a deploy record and on the wire alike — and a refusal that follows a publish keeps its code. The coordinator's reaper fails a non-terminal record whose node stopped answering and deletes terminal ones after 7 days.
- A NODE READS WHAT CHANGED, NOT WHAT EXISTS. `_scafo/changes.json` holds `{v,token}`: a 16-hex token rewritten with a BLIND put (no precondition, last writer wins, fifty concurrent deploys never contend) by the `CasStore` decorator every registry context is built with, after a successful write under `_scafo/applications/`, `_scafo/placement/` or `_scafo/domains/`. It is a HINT — losing one costs latency, bounded by the resync interval, never correctness — so a hint that fails to write is logged and swallowed, and a mutation is never reported as failed because of one. Node records are not hinted (a heartbeat rewrites one every 30s); a node arriving, draining, or changing what it SERVES mints a token explicitly. Each node keeps ONE registry view (`src/core/registry/view.ts`), shared by the reconcile loop, the coordinator and deploy intake: it reads the hint once a pass — one GET, and nothing else when the token has not moved and no timer is up — and otherwise lists the kinds that could have moved and GETs only the records whose `listEntries` ETag differs from the cached one. `CasStore.listEntries` therefore returns an `etag` per entry in the form `get`/`put` answer with, and a listing that carries none is `store-nonconforming`. A refresh that fails keeps the previous view and throws: a registry that could not be read is never "every application was removed". `registry.resyncIntervalMs` (60s) is the bound on a lost hint; `registry.nodeRefreshIntervalMs` (30s) re-reads liveness, which is the AGE of a heartbeat and which no write announces. Operator routes still read the bucket directly — an operator asks rarely and must see the truth — with bounded concurrency rather than a serial loop. The coordinator's assignment pass is SKIPPED outright when neither the applications (their replicas, selectors, retired and blocked state), their placements, nor the live node set changed since the last completed pass: rendezvous hashing over the same inputs can only decide the same thing. The reaper takes ONE listing of `_scafo/deploys/` for the whole installation and caches records by ETag for the life of the coordinator — a terminal deploy never moves again, so a second sweep reads none of them. `GET /v1/deploys/:id` judges a non-terminal deploy whose node stopped answering at READ time, answering `failed`/`deploy-timeout` without writing; the sweep records the same judgement later. The budgets all of this is held to live in `test/scale/baseline.test.ts`, and `pnpm scale` prints them beside what the same installation cost before.
- After a publish the accepting node asks its LOCAL runtime process to adopt now — `POST /reload` on the process's internal listener, behind the runtime driver seam, bounded to a few seconds — and every other node serving the application does the same on the pass that sees the deployment revision move. A reload that fails is one line in the log: Celld's own 30s pointer poll is the fallback, and nothing depends on it having happened. There is no new route and no new record.
- A node takes 64 queued deploys, 4 of them for any one application, one publishing at a time, and is still bounded by `deploy.stagedBytes`. `scafo deploy` retries `deploy-overloaded` honouring the node's `retry-after`, with jittered backoff, until `--queue-timeout` (default 600s, the node's own queue deadline) has passed, printing one line when it starts waiting and one when it is admitted; `--no-wait` fails at once. A retry re-SENDS the staged artifact rather than re-packing it.
- Registry keys are flat and kind-prefixed, one prefix per kind, so listing one kind never reads another's keys and a listing of `_scafo/applications/` is one key per application—the listing every node runs on every reconcile pass. `_scafo/applications/<name>.json` is the application record, `_scafo/trust/<name>.json` its OIDC policy (which may exist BEFORE the application—an admin pre-grants a name and the first deploy creates it), `_scafo/deployments/<name>/<version>.json` and `_scafo/deploys/<name>/<id>.json` its history, `_scafo/placement/<name>.json` its placement, `_scafo/domains/<host>.json` a custom-domain claim, and `fleets/<name>/` is Celld's own keyspace. Every per-application prefix is listed with its trailing separator, so `shop` never reaches `shop-preview` or `shop2`. There is no create command and no create route: the first deploy creates the application, every other setter refuses a missing one with `not-found`, and every mutation is a functional CAS update that preserves the fields it does not own—a deploy can never drop `blocked` or `labels`.
- Run one application-owned process per assigned Scafo node. The supervisor id of that process is the application's name. Celld adopts deployments; retirement or reassignment stops the process. Each deployment a deploy produces is recorded immutably at `_scafo/deployments/<name>/<version>.json`, under the version Celld assigned and nothing else. THE DAEMON NEVER REWRITES OR PARSES THE ARTIFACT'S CONFIG: it locates `wrangler.jsonc`, then `wrangler.json`, at the archive root, refuses an artifact carrying neither with `invalid-input`, and hands that path to `celld deploy --config` untouched, so what the runtime reads is byte for byte what was uploaded. Application configuration is the application's. `scafo deploy --var KEY:VALUE` is the one edit, made client-side before the directory is packed: it is repeatable, splits at the first colon, refuses a name given twice, overrides same-named entries of the config's own `vars`, and goes into the archive only — the project directory is read and never written. `--no-bundle` sets `no_bundle` the same way. With neither flag the archive carries the config as it is. `--name` and `--env` never edit it either: they choose the application, and the config's own `name` reaches Celld as written.
- Publish only routes backed by running processes and the optional platform API apex—never a wildcard application fallback. Every ingress pulls: nothing is pushed into one. A node serves the fleet's routing at `/v1/ingress/routes`, generic or in a format an ingress speaks natively (`/v1/ingress/routes/traefik`); Caddy reads it through the `scafo` dynamic-upstreams module and Traefik through its http provider. Before a node's first reconcile pass has finished, both routes refuse with `ScafoError("draining")`—503—rather than serving an empty document: nothing deployed is an answer a poller acts on, and a node that has just booted does not have one. Operator configuration is the ingress's own and Scafo never rewrites it.
- Deny `/v1/storage` and `/v1/ingress/routes` at the public API apex, matched at a path-segment boundary, and the ingress must enforce that itself rather than trust the daemon behind it. Both surfaces are behind the ingress bearer token, which is the only credential an ingress holds.
- Observability is opt-in: events and access counters are ZSTD Parquet in the bucket; `scafo metrics` and `scafo traces` read them.
- `scafo deployment prune` deletes an application's old Celld deployments (`deploy/<script>/<version>/` and the Scafo deployment record), never a version a Celld pointer names; a pointer that moves onto a selected deployment refuses it as `cas-conflict`. It keeps the newest `--keep` (default 10) and deletes only what is ALSO older than `--older-than` (default 24h) — both gates are always weighed, and `0` lifts the one it is given to. It then collects `deploy-blobs/`: a shared asset blob no kept deployment's `assets.json` references goes once it is older than the same window, after the deployments and without a re-read; an `assets.json` it cannot read refuses the plan as `store-nonconforming`. Prune weighs only what Celld wrote as a deployment — `<script>/<version>/` in Celld's own shapes, a script name it accepts and a hexadecimal version id — and leaves everything else beneath `deploy/` where it is, its `images/` and `queues/` keyspaces (a queue's consumer attachment) above all. `--older-than 0` lifts that protection too, and prune warns that a deploy in flight uploads its blobs before it is visible. A real run prints the plan, then asks at the terminal before it deletes; `--yes` answers ahead of the question, and a run whose input is not a terminal refuses with `invalid-input` rather than take silence for consent. Because it is the one place Scafo reads Celld's own bucket formats, prune is PINNED to the Celld releases this build was verified against: it refuses to plan at all — `--dry-run` included — with `capability-missing`, and there is no override. Every node of the installation still answering (the liveness rule the version-skew gate uses) must report a verified `versions.celld`; an answering node naming no version refuses, nothing answering refuses, and a node that stopped answering is ignored so a retired machine's record cannot block prune forever. Every manifest it lists, kept and deleted alike, must carry a `schema_version` (absent means 1) and `required_features` that build knows, and every `assets.json` it reads a known `schema_version`; a manifest present but unreadable refuses, while a version directory with no manifest at all is a deploy in flight — Celld writes the manifest after the files and before the pointers — and keeps the age-window semantics. `src/core/registry/_celld-contract.ts` holds that contract, every constant permalinked to the upstream lines it mirrors at the commit of a tag, with the procedure for adding a release. The command is unstable until Celld has a deployment lifecycle of its own and warns on every run. CLI warnings go to stderr as `scafo: warning: …`; `SCAFO_SILENCE_WARNINGS=1` silences all of them.
- `_scafo/freeze.json` is the fleet's deploy freeze, set by an ADMIN through `scafo fleet freeze` and lifted by `scafo fleet unfreeze`; its absence means deploys are taken. While it stands, every node refuses deploy intake with `deploys-frozen` (409) before anything is created, and the refusal names when, by whom, why and how it is lifted. It touches nothing else: serving, reconciliation, retirement and `scafo app delete` all carry on, and the first admin's record — stamp and reason — is the one that stands if it is set twice.
- Retiring stops serving and is reversible for the length of a 24h grace; deleting is refused until the grace has run out or `--force` is given, and it removes EVERYTHING of the application — record, trust policy, deployments, deploys, placement, domain claims and the whole `fleets/<name>/` prefix. Blocking is the admin's reversible full stop: `application-blocked` (409), nothing served, no certificates, no deploys, nothing deleted.
- CLI naming: commands address an application with `--name <name>` and optionally `--env <X>`, which addresses `<name>-<env>`; both halves and the join are names, and a join that is not one is `invalid-slug` naming both parts. One client-side resolver (`src/cli/_application.ts`) does it for every command. `scafo deploy` reads `name` from the project directory's `wrangler.jsonc`/`wrangler.json` when `--name` is absent, and never writes it back. Operator scope is `--apps a --apps shop-*`.
- Scafo API and Celld peer listeners default to loopback. Widen only through an explicit private-network or WireGuard decision.

## Packaging

- `patches/citty@0.2.2.patch`, registered under `patchedDependencies` in `pnpm-workspace.yaml`, adds citty's `multiple: true` argument modifier, which `scafo deploy --var` needs to see every occurrence of a repeated flag rather than only the last. It mirrors unjs/citty#259; drop it, potentially unchanged, once citty releases the feature. Anything that installs dependencies has to carry `patches/` with the manifest and the lockfile. citty is a pinned dev dependency bundled into `dist`, never an external import, so every distribution of the CLI runs the patched parser.
- The image runs as uid 10001 with Celld 0.5.0 and esbuild. Its direct Node entrypoint stays PID 1 in a private PID namespace.
- Allow at least 50 seconds for node shutdown. Celld's default may take 40; Docker and Kubernetes grace periods must not be shorter. If `CELLD_SHUTDOWN_TOTAL_MS` is larger, give the enclosing grace at least 10 seconds more.
- Caddy/Traefik share the node network namespace to reach loopback application processes. Multi-node Celld peer traffic needs a trusted wider bind.
- `scripts/install.sh` verifies every download before installation. `scripts/uninstall.sh` preserves `/var/lib/scafo` unless `--purge`; neither mutates the bucket.

## Conventions

- Every setting is readable from three places, with the same precedence everywhere — flag → environment → config file → default. The ones this design added: `registry.resyncIntervalMs` / `SCAFO_REGISTRY_RESYNC_MS` / `--registry-resync-ms` (60000), `registry.nodeRefreshIntervalMs` / `SCAFO_REGISTRY_NODE_REFRESH_MS` / `--registry-node-refresh-ms` (30000), `coordinator.leaseTtlMs` / `SCAFO_COORDINATOR_LEASE_TTL_MS` / `--coordinator-lease-ttl-ms` (45000, renewed at a third), `coordinator.reapIntervalMs` / `SCAFO_COORDINATOR_REAP_INTERVAL_MS` / `--coordinator-reap-interval-ms` (600000). Each is a positive safe integer and anything else is `invalid-input`. `scafo deploy` adds `--queue-timeout <seconds>` and `--no-wait`.
- A list is a REPEATED FLAG on the command line — each occurrence one whole value, nothing split on commas — comma-separated text in an environment variable, which cannot repeat, and a JSON array in the config file.
- ESM, modern TypeScript, explicit `.ts` relative imports; `isolatedDeclarations` requires annotations on exports.
- Prefer Web APIs in core. Use subject-first functions with an options object for multiple arguments. Errors are typed contracts with actionable details and original causes.
- Reuse existing mechanisms; keep modules focused. Prefer one short block comment at a hidden constraint; user docs describe current behavior, not history.
